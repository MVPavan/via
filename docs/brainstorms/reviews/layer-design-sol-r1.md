# Layer design review r1: GPT-6 Sol high

Run: `codex exec -s read-only -m gpt-6-sol -c model_reasoning_effort=high`, codex-cli 0.156.1, 72,928 tokens, 2026-09-25. Same brief for all three reviewers (`scratchpad/council/layer-design/brief.md`, local). Verbatim output; absolute local paths made repo-relative.

## Verdict: SOUND WITH CHANGES

The six layers put most responsibilities in sensible places, and route changes can stay behind C1 and C2. The draft needs a process decision and tighter contracts for detached control, vendor requests, and run identity before those boundaries are reliable.

### Findings

1. **[blocking] The proposed shared host conflicts with a recorded owner decision.** The current invariant says **no daemon, one worker per run** (`.repo-context/invariants.md:23`, `docs/brainstorms/README.md:364`). The draft instead has a detached host multiplexing runs on a shared vendor server, while calling its owner an open question (`docs/brainstorms/system-layers.md:309`, `docs/brainstorms/system-layers.md:328`). **Fix:** put the choice to the owner explicitly: retain one worker and use per-run vendor servers, or revise the no-daemon invariant and specify the shared host’s lifetime, discovery, configuration key, and shutdown rules. The latter may best meet R2 at concurrency, but it is not authorized by the current invariant.

2. **[blocking] Detached runs have no defined control or takeover path.** C1 exposes later `steer` and `cancel` calls; the spawning CLI exits; leases say another process can take over (`docs/brainstorms/system-layers.md:22`, `docs/brainstorms/system-layers.md:245`, `docs/brainstorms/system-layers.md:303`). A Store lease alone cannot deliver a command to the live host or reconnect to a lost stdio stream. **Fix:** define authenticated local control delivery with durable command IDs and acknowledgements, atomic lease fencing, and process identity checks. Specify takeover separately for a live host, a dead host with a live vendor child, and a lost shared server. An in-flight prompt with an unknown outcome must remain unknown, never be resent automatically, as the launch-receipt rule requires (`docs/brainstorms/access-methods.md:405`). Marking such a run failed is a safe outcome; it is not continuation of the running turn.

3. **[major] Vendor-initiated requests stop at C3.** L4 owns server requests, but C2 returns only events, failures, capabilities and a session ID; C1 has no way to resolve a pending request (`docs/brainstorms/system-layers.md:14`, `docs/brainstorms/system-layers.md:22`). The supplied Codex schema includes approval, user-input and MCP elicitation requests (`scratchpad/codex-schema/ServerRequest.json:1901`, `scratchpad/codex-schema/ServerRequest.json:1921`, `scratchpad/codex-schema/ServerRequest.json:1951`). **Fix:** add a correlated pending-request/response path through C2, with adapter-owned interpretation and a deadline. For a headless run, define a deterministic agent-native answer or refusal; if caller input is supported, expose a narrow handle-authorized C1 response verb. Answering an agent request is necessary protocol handling, not a VIA permission-enforcement layer.

4. **[major] Run, turn and session identity are inconsistent.** The glossary calls a run one execution of a prompt; the record diagram permits many runs per session, while the state machine resumes an *Idle run* and the queue belongs to a session (`.repo-context/CONTEXT.md:52`, `docs/brainstorms/system-layers.md:225`, `docs/brainstorms/system-layers.md:354`). Only `cancel` and `steer` explicitly check the starter’s handle. **Fix:** define whether each resumed prompt creates a new run ID or a new turn within one run, then state which handle authorizes resume, queued prompts, cancellation and session closure. Persist route, adapter version and effective native bounds with the session so resume cannot silently change them. A new run may choose another route; an existing run cannot (`docs/brainstorms/access-methods.md:202`).

5. **[major] A raw tap cannot produce isolated per-run logs on a shared connection.** L5 writes bytes before parsing, yet the Store records a raw-log path per run; a shared server’s stdio carries interleaved traffic for several runs (`docs/brainstorms/system-layers.md:292`, `docs/brainstorms/system-layers.md:334`, `docs/brainstorms/system-layers.md:362`). **Fix:** keep an append-only *connection* transcript at L5. Have L4 correlate request IDs and session IDs, then index per-run events and offsets above it. Define ordering for inbound messages, normalized events and terminal state; prevent one run’s `logs` call from exposing another run’s traffic.

6. **[major] Deadline and flow-control ownership is missing.** A timeout appears as a failure state, but no layer owns its clock, bounded output drain, Store-stall behavior, or the transition from native interrupt to forced tree termination (`docs/brainstorms/system-layers.md:218`, `docs/brainstorms/access-methods.md:431`). Pi RPC can stall when stdout is not drained, and the benchmark did not test cleanup after a tool had begun executing (`docs/brainstorms/access-methods.md:347`, `scratchpad/headless-bench/analysis.md:85`). **Fix:** L2 owns deadlines and per-session queue limits; L4 correlates and orders protocol messages; L5 drains into bounded storage without blocking pipe reads; L6 performs timed escalation and records whether a tool tree actually exited. C2 should distinguish requested interrupt, confirmed cancellation, forced termination and unknown outcome.

### Contract and harness assessment

**Keep the six boundaries and the side Store.** C3 is a useful boundary for protocol-specific typed clients, but `open/close/health` is about all that is genuinely common across CLI, HTTP/SSE, ACP and vendor RPC. Do not force their verbs into one universal Route interface. Likewise, move request-ID pairing out of the supposedly protocol-neutral C4 description and into L4 where needed (`docs/brainstorms/system-layers.md:24`). L4 and L5 need not be separate packages until reuse justifies it; their responsibility split is clear.

I checked all 20 rows of the local harness matrix (`docs/brainstorms/access-methods.md:209`). **No listed active harness is proven to require a different C1 or C2 shape** if capabilities can be partial or refused by name. Pi and OMP need separate RPC semantics; Cursor’s CLI loses SDK-only status, cancel and billing; Copilot’s direct runtime route remains unverified; Antigravity and Amp rely mainly on CLI behavior; the ACP candidates depend on per-agent resume and native-bound probes. Kimi is archived and explicitly outside the proposed routes. This supports the *interface* premise, not equal lifecycle capability across harnesses. A route change can alter capabilities, native bounds, process costs and failure modes; C1 must report those accurately, and C2 must carry the outcomes above. The current C2 needs the request and cancellation additions first. Inference: if R1 means every verb must succeed on every harness, the route decision cannot meet it; the recorded named-refusal rule gives R1 the workable interpretation (`.repo-context/invariants.md:18`).

### First prototype and verification limits

First prototype the **cross-process lifecycle**, after the owner resolves the process topology: fake CLI and multiplexed server peers, two concurrent callers, queued resume, output flood, Store contention, host crash during a tool, lease fencing, cancel escalation and server loss. Then probe Codex app-server and the distinct Pi/OMP cancel paths. This targets the contracts most likely to force redesign before writing many adapters.

This was a read-only review of local records and generated schema; I ran no agents or live vendor probes. Direct Copilot runtime use, OMP cancel settlement, broad native ACP resume behavior, and cleanup during an executing tool remain unverified in the cited material (`docs/brainstorms/access-methods.md:591`, `docs/brainstorms/reviews/routes-decision-r1-consolidated.md:69`).
