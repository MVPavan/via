## Claude Agent SDK — Python and TypeScript

### Identity and architecture

The packages are `claude-agent-sdk` on PyPI and `@anthropic-ai/claude-agent-sdk` on npm, maintained in Anthropic’s [Python repo](https://github.com/anthropics/claude-agent-sdk-python) and [TypeScript repo](https://github.com/anthropics/claude-agent-sdk-typescript). The Python package is MIT licensed; at the version/date checked it was **0.2.159**, released September 23, bundling Claude Code CLI **2.1.281**. Its PyPI classifier says **Alpha**. The TypeScript package is also vendor-maintained; the precise npm version and an explicit maturity label on September 24 are **UNVERIFIED**. [Python PyPI release](https://pypi.org/project/claude-agent-sdk/0.2.159/), [Python repo metadata](https://github.com/anthropics/claude-agent-sdk-python/blob/main/pyproject.toml), [TypeScript repo](https://github.com/anthropics/claude-agent-sdk-typescript)

This is not an in-process model loop or a direct API client. Anthropic describes the SDK as a library that runs the Claude Code binary; Python’s README says it bundles the CLI by default and permits a system CLI or custom `cli_path`. Python source implements the subprocess transport. The CLI receives options and input over stdio; the SDK parses and returns typed messages. [SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), [Python README](https://github.com/anthropics/claude-agent-sdk-python), [Python subprocess transport source](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/_internal/transport/subprocess_cli.py)

### How close it is to `claude -p`

Anthropic says the SDK provides the same tools, agent loop, and context management as Claude Code, including file read/write/edit, command execution, web search, hooks, subagents, MCP, permissions, sessions, skills, commands, and plugins. It can do repository coding work. It is not automatically identical in configuration or prompt behavior, however; Anthropic documents `claude -p --output-format json` as the way to drive the same agent loop from other languages. [SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

The important current defaults are:

- **Settings and project instructions:** For both SDKs, omitted `settingSources` / `setting_sources` makes `query()` load user, project, and local filesystem settings like the CLI. `"project"` includes `CLAUDE.md`, rules, skills, commands, and subagents; `"user"` and `"local"` load their corresponding scopes. Passing `[]` opts out of those filesystem sources. Endpoint-managed policy still loads. This default has changed across SDK releases, so pin and check the version. [Python reference](https://code.claude.com/docs/en/agent-sdk/python), [Claude Code features](https://code.claude.com/docs/en/agent-sdk/claude-code-features)
- **System prompt:** Do not assume SDK prompt parity from the shared agent loop. The SDK supports a configurable prompt and a `claude_code` preset; set that preset when CLI-style Claude Code prompt behavior is required. The exact effective prompt also depends on the SDK/CLI versions and loaded settings. [Python reference](https://code.claude.com/docs/en/agent-sdk/python), [prompt configuration](https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts)
- **Skills, slash commands, plugins, and subagents:** These can be loaded from the filesystem or configured through SDK options. Their discovery depends on sources and paths; plugins can be loaded by local path. They are not a guarantee that every CLI-installed integration is visible to every SDK invocation. [Claude Code features](https://code.claude.com/docs/en/agent-sdk/claude-code-features), [SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- **Permissions:** SDK options expose permission modes, tool allow/deny lists, and permission callbacks. The agent still runs through the CLI permission machinery; configure and validate the mode rather than assuming interactive `claude -p` behavior. [Permissions reference](https://code.claude.com/docs/en/agent-sdk/permissions)
- **Sessions:** Python can list, inspect, continue, and resume sessions; `ClaudeSDKClient` keeps one live session for multiple exchanges. Session files are managed by the CLI. SDK-created sessions use Claude Code’s session machinery, but full interoperability with every CLI invocation pattern is **UNVERIFIED**. [Python reference](https://code.claude.com/docs/en/agent-sdk/python), [sessions guide](https://code.claude.com/docs/en/agent-sdk/sessions)

### Authentication and subscription terms

The SDK’s subprocess uses Claude Code authentication. Thus, a local `claude` login can be picked up by the SDK unless an API key or another configured provider takes precedence. Anthropic’s support guidance says API-key authentication is the preferred path for third-party tools, and warns that certain third-party use may be charged to usage credits rather than plan limits. An environment API key can also take precedence over a subscription login. [Login guidance](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account), [API-key environment variables](https://support.claude.com/en/articles/12304248-manage-api-key-environment-variables-in-claude-code)

The current [Agent SDK plan article](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan), dated June 16 with a June 15 update, says: **“For now, nothing has changed: Claude Agent SDK, `claude -p`, and third-party app usage still draw from your subscription's usage limits.”** The earlier announced separate monthly credits are explicitly paused and unavailable. Therefore, SDK and `claude -p` billing currently uses plan limits according to that article; do not rely on the superseded credit schedule.

The separate SDK overview policy is explicit: **“Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK.”** For a local VIA run used by its account owner, the current billing article confirms technical/billing use; Anthropic’s login guidance nevertheless prefers API-key authentication for third-party tools. The sources do **not** clearly state a blanket permission for every personal automation scenario. For VIA distributed as a product, the SDK overview requires prior approval to offer users Claude login or subscription rate limits; use API-key authentication or a supported cloud provider for a product unless Anthropic approves otherwise. [SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), [login guidance](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account)

Claude supports Anthropic API keys and documented cloud-provider paths such as Bedrock and Vertex AI. The exact enterprise authentication path depends on the organization’s Claude Code configuration. **UNVERIFIED:** whether every enterprise SSO/managed credential path works identically in both SDK languages and all supported CLI versions. [Agent SDK quickstart](https://code.claude.com/docs/en/agent-sdk/quickstart), [Claude Code on Bedrock](https://docs.anthropic.com/en/docs/claude-code/amazon-bedrock), [Claude Code on Vertex AI](https://docs.anthropic.com/en/docs/claude-code/google-vertex-ai)

### VIA lifecycle and operational limits

Python `query()` streams typed messages and structured results, but does not support interruption. Use `ClaudeSDKClient` for multi-message streaming input and interruption. TypeScript supports streaming input, but confirmed **mid-turn steer semantics are UNVERIFIED**; supplying another input stream is not, by itself, proof that input interrupts a currently running tool or model step. [Python API reference](https://code.claude.com/docs/en/agent-sdk/python), [streaming input](https://code.claude.com/docs/en/agent-sdk/streaming-input)

The SDK supports structured JSON-schema output, cost and token usage reporting, and model/effort selection through CLI-backed options. It is therefore viable for spawn/result and session continuation. It does not provide the same explicit `status` surface as a long-lived server protocol; VIA should track the process/session and streamed terminal result itself. [Structured output](https://code.claude.com/docs/en/agent-sdk/structured-outputs), [cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking), [Python reference](https://code.claude.com/docs/en/agent-sdk/python)

Operational cautions: the Python SDK bundles a CLI, checks minimum versions, and may differ from a separately installed `claude`; pin the SDK and note the bundled CLI version. The TypeScript SDK also spawns a CLI child. That means a library call has child-process, memory, and version-coupling costs. A Python issue reports that CLI version-check timeout handling can hang while waiting for termination; a TypeScript issue reports high memory use when listing sessions. Those are issue reports, not proof they affect every current release. [Python release/changelog](https://github.com/anthropics/claude-agent-sdk-python/blob/main/CHANGELOG.md), [timeout issue](https://github.com/anthropics/claude-agent-sdk-python/issues/1162), [TypeScript session-list issue](https://github.com/anthropics/claude-agent-sdk-typescript/issues/268)

**Verdict:** Keep `claude -p --output-format stream-json` as VIA’s default adapter route. It is directly documented for scripting, works from any implementation language, and avoids treating a wrapper library as a different runtime. Consider the Python Agent SDK as an opt-in route when interruption, typed results, or SDK-specific facilities justify the bundled CLI and session/configuration complexity. Do not offer Claude subscription login through a distributed VIA product without prior approval. [CLI reference](https://docs.anthropic.com/en/docs/claude-code/cli-usage), [SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

## OpenAI Codex SDK — TypeScript and Python

### Identity and architecture

The TypeScript package is `@openai/codex-sdk` in [`openai/codex`](https://github.com/openai/codex/tree/main/sdk/typescript), Apache-2.0. The Python package is `openai-codex`, imported as `openai_codex`, from the same Apache-2.0 repository. On September 23, PyPI published Python **0.156.1**, requiring Python 3.10+, with **Production/Stable** classifier. The current source-tree manifests show development placeholder versions (`0.0.0-dev`), so use registry releases for actual package versioning. The exact npm SDK release version and its formal maturity label on September 24 are **UNVERIFIED**. [Python PyPI release](https://pypi.org/project/openai-codex/0.156.1/), [TypeScript package source](https://github.com/openai/codex/blob/main/sdk/typescript/package.json), [Codex Python SDK](https://github.com/openai/codex/tree/main/sdk/python)

These SDKs use different underlying routes:

- **TypeScript:** the README says it wraps the `codex` CLI, spawns it, and exchanges JSONL events over stdin/stdout. It is a typed wrapper around `codex exec`, not a direct cloud API client. [TypeScript README](https://github.com/openai/codex/blob/main/sdk/typescript/README.md), [TypeScript source](https://github.com/openai/codex/tree/main/sdk/typescript/src)
- **Python:** installs a matching `openai-codex-cli-bin` runtime dependency and starts `codex app-server --listen stdio://`; the SDK speaks JSON-RPC to that child. It exposes the app-server’s thread/turn control API rather than spawning a separate `exec` process for each call. [Python getting started](https://github.com/openai/codex/blob/main/sdk/python/docs/getting-started.md), [Python client source](https://github.com/openai/codex/blob/main/sdk/python/src/openai_codex/client.py)

Both run the Codex agent locally against the selected workspace and can read, write, and run code under configured permissions. Python exposes Codex app-server thread and turn lifecycle controls. The route and interface differ from the interactive TUI, so “same agent” means the Codex runtime, not an identical interactive experience. [Codex Python SDK](https://github.com/openai/codex/tree/main/sdk/python), [Codex CLI getting started](https://help.openai.com/en/articles/11096431)

### Equivalence to CLI and lifecycle

The TypeScript SDK returns structured items and final response, and offers streamed events. Threads can continue across multiple runs, but the SDK is layered over CLI JSONL and does not document mid-turn steering. It can start and resume work; steering should be declared unsupported unless verified independently. **UNVERIFIED:** a reliable public SDK-level cancel API in the version available on September 24. A caller could terminate the child process, but process termination is not the same guarantee as an app-server interrupt. [TypeScript README](https://github.com/openai/codex/blob/main/sdk/typescript/README.md), [TypeScript source](https://github.com/openai/codex/tree/main/sdk/typescript/src)

Python provides `Codex` and `AsyncCodex`, start/resume/fork thread operations, streaming turn handles, usage-bearing results, `turn_steer`, and `turn_interrupt`. This is the strongest direct fit of the SDKs researched here for VIA’s `spawn`, `resume`, `steer`, `cancel`, and `result` verbs. It is built on a shared app-server client and can hold multiple threads; use per-thread identifiers and correlate notifications. [Python API reference](https://github.com/openai/codex/blob/main/sdk/python/docs/api-reference.md), [Python client source](https://github.com/openai/codex/blob/main/sdk/python/src/openai_codex/client.py)

The Python SDK exposes sandbox choices and approval modes, model/provider selection, and structured `TurnResult` data including token usage. It resumes stored Codex threads by ID. Codex’s app-server has the relevant thread APIs, but whether every SDK-created thread is interchangeable with every CLI resume flow is **UNVERIFIED** from the cited documentation. **UNVERIFIED:** the TypeScript SDK’s cost-reporting completeness and a general status-by-thread API comparable to Python’s app-server control surface. [Python API reference](https://github.com/openai/codex/blob/main/sdk/python/docs/api-reference.md), [Python getting started](https://github.com/openai/codex/blob/main/sdk/python/docs/getting-started.md)

### Authentication and terms

PyPI and the project README explicitly say that Python reuses existing Codex authentication and supports ChatGPT browser login, device-code login, and API-key login. Thus it can use the user’s local Codex ChatGPT account session. The TypeScript wrapper invokes Codex CLI and inherits its local authentication. Codex supports API-key configuration and provider configuration; the exact set of providers depends on the pinned app-server release. [Python PyPI page](https://pypi.org/project/openai-codex/0.156.1/), [Python README](https://github.com/openai/codex/blob/main/sdk/python/README.md), [Codex CLI ChatGPT sign-in](https://help.openai.com/en/articles/11381614-api-codex-cli-and-sign-in-with-chatgpt)

OpenAI’s [Codex plan usage help](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan) says Codex usage is limited by plan, with allowances/credits shared with specified ChatGPT features where available. [Codex CLI sign-in help](https://help.openai.com/en/articles/11381614-api-codex-cli-and-sign-in-with-chatgpt) describes Sign in with ChatGPT and notes that it links identity to an API account and stores credentials locally. This makes local use through Codex’s documented auth path technically supported.

There is a terms caveat: the [OpenAI Consumer Terms](https://openai.com/policies/terms-of-use) say users may not **“Automatically or programmatically extract data or Output”** from OpenAI Services. The sources reviewed do not specifically reconcile that broad wording with official Codex CLI/SDK use under a ChatGPT sign-in. OpenAI separately documents Codex SDK/CLI as developer tools and supports ChatGPT-plan Codex usage, but I cannot conclude from the cited material that the Consumer Terms clause is inapplicable to all programmatic SDK use. For a product offered to others, do not treat an individual’s ChatGPT session as a service credential; verify the applicable commercial/API agreement and product authorization. [Python SDK docs](https://github.com/openai/codex/tree/main/sdk/python), [Codex plan usage](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan), [Consumer Terms](https://openai.com/policies/terms-of-use)

### Pitfalls and VIA recommendation

The Python SDK bundles a CLI runtime version, so pin Python SDK and runtime together; the getting-started guide says stable SDK releases track the corresponding stable Codex CLI release. The TypeScript SDK also depends on the CLI package. A June issue reported that the SDK README installation omitted the runtime CLI package dependency; confirm installation resolution for the chosen npm release. A September Python issue reports that a startup timeout can leave app-server running and make client reuse fail. Treat both as version-specific reports and test pinned releases before relying on them. [Python getting started](https://github.com/openai/codex/blob/main/sdk/python/docs/getting-started.md), [TypeScript install issue](https://github.com/openai/codex/issues/25533), [Python timeout issue](https://github.com/openai/codex/issues/46903)

**Verdict:** For VIA’s default route, use `codex exec --json` where one process per turn is sufficient. Add the Python SDK as an explicit Codex app-server route when VIA needs mid-turn steering, interrupt, thread resume/fork, or structured usage. Keep TypeScript SDK as a wrapper option when the caller is already Node-based; it does not offer the same documented lifecycle depth as the Python SDK. [Codex TypeScript README](https://github.com/openai/codex/blob/main/sdk/typescript/README.md), [Codex Python API reference](https://github.com/openai/codex/blob/main/sdk/python/docs/api-reference.md)
