## OpenCode SDK (`@opencode-ai/sdk`)

**Identity and process.** The official TypeScript package is MIT-licensed. The npm registry showed `1.18.31` on the day checked; the repository’s development-branch package file showed `1.18.32`, so pin the published package version rather than assuming repository-head parity. I found no GA/beta label. The SDK’s `createOpencode` starts a server and client; source shows it launches the `opencode` executable with `serve`, so it expects a system CLI rather than bundling one. [npm package](https://www.npmjs.com/package/%40opencode-ai/sdk?activeTab=code), [package source](https://github.com/anomalyco/opencode/blob/dev/packages/sdk/js/package.json), [server launcher source](https://github.com/anomalyco/opencode/blob/dev/packages/sdk/js/src/server.ts), [SDK docs](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/sdk.mdx)

**CLI equivalence and lifecycle.** It controls the OpenCode server/runtime, not a separate API-only agent. It offers sessions, messages, events, and configuration; the server loads `opencode.json` and accepts inline overrides. The SDK source confirms the child-process boundary, but it does not establish exact defaults for every CLI feature (tools, project instructions, skills, commands, hooks, subagents, MCP, permissions, settings). Session data belongs to OpenCode’s server/runtime. Mid-turn steering and SDK-level usage/cost parity are **UNVERIFIED** here; the SDK’s `AbortSignal` applies to server startup, not proof of turn cancellation. [SDK docs](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/sdk.mdx), [server launcher source](https://github.com/anomalyco/opencode/blob/dev/packages/sdk/js/src/server.ts)

**Auth and subscription terms.** Provider authentication is held in OpenCode’s local auth store. OpenCode documents ChatGPT Plus, GitHub Copilot, GitLab Duo, and SuperGrok paths. It says: “There are plugins that allow you to use your Claude Pro/Max models with OpenCode. Anthropic explicitly prohibits this.” The OpenCode docs also describe Claude Pro/Max selection, but the same page warns about plugin use; don’t interpret a visible option as permission. [OpenCode provider docs](https://opencode.ai/docs/providers)

Anthropic’s current help-center page says: “For now, nothing has changed: Claude Agent SDK, `claude -p`, and third-party app usage still draw from your subscription’s usage limits.” It lists both use in a developer’s own projects and third-party apps using a user’s subscription, while clarifying that its previously announced monthly SDK credit is not in effect. That settles current billing treatment in that help article, but it does **not** establish a blanket legal authorization for every third-party harness. The claim that Anthropic prohibits Claude subscription use through third-party harnesses is confirmed by OpenCode’s warning for the plugin route; the broader SDK/product permission boundary remains **UNVERIFIED** from the current primary sources retrieved. [Anthropic Help Center, June 16, 2026](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)

**VIA verdict.** Keep CLI for one-shot runs; use the SDK/server route when persistent sessions or status queries matter. Make auth eligibility and an external write boundary explicit. The SDK is a typed client around a hidden child process, so it doesn’t eliminate CLI version coupling.

## Cline SDK (`@cline/sdk`)

**Identity and process.** Official Cline project, Apache-2.0; npm showed `0.0.86` on Sep 24, 2026. The SDK docs call `@cline/core` experimental. The SDK is an in-process TypeScript agent stack: `@cline/agents` owns the loop and tools; `@cline/core` adds session lifecycle, persistence, config discovery, and default tools. It does not shell out to `cline` for local execution. [npm package](https://www.npmjs.com/package/%40cline/sdk), [SDK README](https://github.com/cline/cline/blob/main/sdk/README.md), [architecture](https://github.com/cline/cline/blob/main/sdk/ARCHITECTURE.md)

**CLI equivalence and lifecycle.** Cline says it is “the same engine that powers Cline,” and documents built-in file, shell, search, and web tools; sessions, approvals, plugins, hooks, MCP, teams, and hub support exist across SDK packages. However, the example `Agent` takes an explicit prompt, provider, model, and tool list; that is not evidence that every SDK invocation inherits the CLI’s complete settings or permission configuration. `ClineCore` exposes session artifacts/results. Mid-turn steering and complete parity for slash commands, project instructions, and CLI session sharing are **UNVERIFIED**. [SDK README](https://github.com/cline/cline/blob/main/sdk/README.md), [ClineCore sessions docs](https://docs.cline.bot/cline-sdk/sessions)

**Auth and terms.** The SDK supports provider/API integrations. Cline’s CLI documents Cline account auth, ClinePass, BYOK, and ChatGPT subscription OAuth, but I found no primary-source confirmation that an SDK session automatically imports that CLI OAuth credential or offers the same subscription route. Cline’s own billing is not the same as an upstream provider subscription. Whether OpenAI permits ChatGPT subscription credentials through this third-party runtime is **UNVERIFIED**. [Cline authorization docs](https://github.com/cline/cline/blob/main/docs/getting-started/authorizing-with-cline.mdx), [Cline CLI README](https://github.com/cline/cline/blob/main/apps/cli/README.md)

**VIA verdict.** Prefer CLI/ACP unless VIA specifically needs Cline’s in-process runtime. Before offering Cline SDK as a personal-subscription route, verify credential pickup and upstream terms directly.

## Pi coding-agent SDK (`@earendil-works/pi-coding-agent`)

**Identity and process.** Official Earendil Works repository, MIT; npm showed version `0.87.1`, published Sep 22. It provides a TypeScript SDK and in-process agent session, not a wrapper around the `pi` CLI. No formal maturity label found. [npm package](https://www.npmjs.com/package/%40earendil-works/pi-coding-agent), [SDK docs](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)

**CLI equivalence and lifecycle.** The SDK creates the same agent session with typed event subscriptions, configurable tools, and a resource loader. Defaults can discover extensions, skills, prompt templates, themes, and context files. The docs explicitly support in-memory or file-backed sessions, resume/open/list/fork, settings management, and auth storage. The API offers direct session prompt/control; the exact semantics of mid-turn steering and cancel should be contract-tested before VIA advertises them. Usage statistics are available at the session layer. It can do repository work with read/bash/edit/write tools, but it is configurable rather than a promise of identical TUI behavior. [SDK docs](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)

**Auth and terms.** Pi supports provider credentials and OAuth flows in its runtime; the SDK can discover Pi’s auth storage. That does not mean it reuses Claude Code, ChatGPT, or Copilot CLI credentials. The SDK’s ability to authenticate is distinct from upstream authorization for personal-subscription automation; those terms are **UNVERIFIED** here. [Pi package documentation](https://www.npmjs.com/package/%40earendil-works/pi-coding-agent)

**VIA verdict.** Strong SDK/RPC candidate for lifecycle-rich integration. Pin Pi and its runtime dependencies; probe cancellation/steering behavior and record exactly which auth source is used.

## Oh My Pi SDK (`@oh-my-pi/pi-coding-agent`)

**Identity and process.** Stencil Labs’ MIT-licensed Pi fork. npm showed `18.3.0` on Sep 24, while the GitHub releases page showed `18.2.11` released Sep 23; that version-channel discrepancy is a pinning risk. Bun/TypeScript host API embeds the session in-process. The same project includes a Rust N-API addon for native tools and an RPC mode for process isolation. No maturity label found. [npm package](https://www.npmjs.com/package/%40oh-my-pi/pi-coding-agent), [GitHub releases](https://github.com/can1357/oh-my-pi/releases), [SDK docs](https://github.com/can1357/oh-my-pi/blob/main/docs/sdk.md), [repo README](https://github.com/can1357/oh-my-pi)

**CLI equivalence and lifecycle.** Documentation calls this the same engine across TUI, one-shot, SDK, RPC, and ACP. Its SDK exposes session events, tools, model/auth/resource discovery, and session managers; default SDK setup discovers MCP servers. Sessions can be in-memory or persistent and support resume/open/list/fork. The SDK’s runtime can do repo coding and has a large built-in tool surface. Exact lifecycle mapping of cancel/steer and settings parity needs a version-pinned probe; issues document that large persisted transcripts can make resume very slow. [SDK docs](https://github.com/can1357/oh-my-pi/blob/main/docs/sdk.md), [MCP lifecycle](https://github.com/can1357/oh-my-pi/blob/main/docs/mcp-runtime-lifecycle.md), [resume-performance issue](https://github.com/can1357/oh-my-pi/issues/9553)

**Auth and terms.** Provider OAuth and API-key behavior belongs to OMP’s provider/auth system. I did not verify an upstream provider’s authorization for OMP to use any particular consumer subscription. **UNVERIFIED.**

**VIA verdict.** Prefer OMP’s RPC adapter if VIA should be language-independent and isolated. Use the in-process SDK only if VIA accepts Bun, native-addon, and fast-moving-version coupling.

## Kimi / Moonshot Agent SDK

**CLI equivalence and lifecycle.** Moonshot says the SDK reuses CLI configuration, tools, skills, and MCP servers. TypeScript sessions provide streamed events, multi-turn prompts, and close; the README does not establish resume, structured final object, token/cost reporting, steer, or concurrent-session guarantees. Assume CLI/wire-version coupling until pinned and tested. [Kimi SDK README](https://github.com/MoonshotAI/kimi-agent-sdk), [Python quickstart](https://github.com/MoonshotAI/kimi-agent-sdk/blob/main/guides/python/quickstart.md)

**Auth and terms.** The Python guide says credentials follow the Kimi Code configuration model and documents API-key environment variables. The SDK source reviewed did not establish that a personal Kimi app plan works through the SDK, nor did I find primary terms settling automation or third-party-product use. **UNVERIFIED.** [Python quickstart](https://github.com/MoonshotAI/kimi-agent-sdk/blob/main/guides/python/quickstart.md)

**VIA verdict.** The wire SDK may improve stream handling, but the documented lifecycle is thinner than VIA needs. Prefer the CLI or protocol adapter until current supported CLI identity and lifecycle capabilities are confirmed.

## Qwen Code SDK

**Identity and process.** Qwen’s official TypeScript package is `@qwen-code/sdk`; docs also identify Python package `qwen-code-sdk` and a Java artifact `com.alibaba:qwencode-sdk`. The TypeScript SDK is explicitly described as “minimum experimental.” TS bundles Qwen CLI by default; Python requires an external `qwen` executable in v1. The Java SDK docs describe daemon transport plus legacy stdio. [TypeScript SDK README](https://github.com/QwenLM/qwen-code/blob/main/packages/sdk-typescript/README.md), [Python SDK docs](https://github.com/QwenLM/qwen-code/blob/main/docs/developers/sdk-python.md), [Java SDK docs](https://github.com/QwenLM/qwen-code/blob/main/docs/developers/sdk-java.md)

**CLI equivalence and lifecycle.** The SDK runs the Qwen Code runtime. TS provides a streamed `query`, multi-turn input, interrupt/close, model and permission changes, session ID/status checks, and optional daemon session load/resume. It exposes CLI tools, permissions, system prompt presets, and MCP configuration. The Python client targets the existing `stream-json` CLI protocol and includes interrupt/model/permission controls. These surfaces are not parity-equivalent: only TS currently documents the daemon client; interactive question handling has had SDK gaps. [TypeScript SDK docs](https://github.com/QwenLM/qwen-code/blob/main/docs/developers/sdk-typescript.md), [architecture](https://github.com/QwenLM/qwen-code/blob/main/docs/developers/architecture.md), [SDK interaction gap issue](https://github.com/QwenLM/qwen-code/issues/6647)

**Auth and terms.** Qwen Code supports OAuth and API-key modes, but I did not verify that a consumer Qwen plan can be used through each SDK or obtain a primary terms statement for personal automation or products offered to others. **UNVERIFIED.**

**VIA verdict.** The SDK is lifecycle-richer than the one-shot CLI, but experimental and coupled to CLI versions. Start with CLI/ACP; selectively adopt the TS daemon API after pinning and validating load/resume/cancel. Do not infer Python/Java parity.

## Goose

**Identity and process.** Goose is AAIF’s Apache-2.0 Rust project. Its GDK exposes Rust/Python/Kotlin-related artifacts; a current release set/version for each binding was not confirmed in the registry pages retrieved. Official repository guidance says the GDK crate set is release-managed. The GDK is a library/FFI surface, not merely a CLI wrapper. [Goose repository](https://github.com/aaif-goose/goose), [workspace manifest](https://github.com/aaif-goose/goose/blob/main/Cargo.toml), [GDK release guidance](https://github.com/aaif-goose/goose/blob/main/AGENTS.md)

**CLI equivalence and lifecycle.** Goose’s agent runtime is in the Rust project, but the GDK’s current maturity is a material limitation: maintainers state that the Rust/Kotlin/Python GDK still needs the unrolled agent loop and compaction. Thus “SDK exists” does not mean a complete coding-agent lifecycle API exists. Goose’s CLI supports ACP, and Goose can itself use external ACP agents. [GDK API issue](https://github.com/aaif-goose/goose/issues/11098), [architecture](https://github.com/aaif-goose/goose/blob/main/documentation/docs/goose-architecture/goose-architecture.md)

**Auth and terms.** Provider authentication depends on the configured provider. I found no primary-source confirmation that Goose GDK accepts or is allowed to reuse consumer subscriptions such as ChatGPT Plus or Claude Pro/Max. **UNVERIFIED.**

**VIA verdict.** Use Goose CLI/ACP for a coding-agent adapter. Do not choose GDK for VIA’s lifecycle contract until the full agent loop is documented and available in the binding.

Those capabilities are the HTTP API surface; they should not be attributed automatically to the Python library. The library guide does not establish parity for settings, CLI commands/hooks/subagents, or cancellation. [Python library guide](https://github.com/hermes-agent-org/hermes/blob/main/website/docs/guides/python-library.md), [programmatic integration/API guide](https://github.com/NousResearch/hermes/blob/main/website/docs/developer-guide/programmatic-integration.md)

**Auth and terms.** The guide requires provider API-key environment variables. The project also documents Nous Portal and provider-specific auth, but personal subscription reuse and third-party-product terms were not settled by the sources reviewed. **UNVERIFIED.** [Python library guide](https://github.com/hermes-agent-org/hermes/blob/main/website/docs/guides/python-library.md)

**VIA verdict.** Prefer the documented HTTP Runs API if it is enabled and locally authenticated. Use the Python library only with version pinning and acceptance that its internal API may change; use CLI for simpler one-shot execution.

## Terms and interpretation

The personal-subscription answer must be made **per upstream provider and per auth mechanism**, not per adapter alone. A locally run SDK can still send a user’s subscription OAuth credential through third-party code.

Anthropic’s help center currently says that Claude Agent SDK, `claude -p`, and third-party-app use continue drawing from subscription limits; its page explicitly says the proposed credit change is paused. OpenCode’s provider docs separately state that Anthropic prohibits the Claude Pro/Max plugin route. Together these support a narrow conclusion: **the broad report that every local SDK use is categorically disallowed is not established by the current sources retrieved; the OpenCode plugin path is explicitly called prohibited.** Third-party product authorization remains unresolved. [Anthropic Help Center](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan), [OpenCode provider docs](https://opencode.ai/docs/providers)

OpenAI’s Terms of Use page retrieved contains the sentence **“Automatically or programmatically extract data or Output (defined below).”** This is a direct quote, but the page found in search was a dated terms version and does not settle how OpenAI treats a particular Codex/OAuth adapter today. Treat ChatGPT-subscription use through third-party coding harnesses as **UNVERIFIED** pending the current applicable terms and product-specific documentation. [OpenAI Terms of Use page retrieved](https://openai.com/en-GB/policies/oct-2024-row-terms/)

For Cline/ChatGPT OAuth, Pi/OpenAI Codex OAuth, OpenCode’s ChatGPT or Copilot routes, and other vendors’ consumer plans, I did not establish current first-party terms permitting both personal automation and embedding in a third-party product. Those remain **UNVERIFIED** above.
