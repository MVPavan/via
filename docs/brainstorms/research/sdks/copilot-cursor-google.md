## GitHub Copilot SDK

**Identity and runtime.** GitHub maintains the official MIT-licensed SDKs: `@github/copilot-sdk`, `github-copilot-sdk`, Go module `github.com/github/copilot-sdk/go`, `GitHub.Copilot.SDK`, Maven `com.github:copilot-sdk-java`, and crate `github-copilot-sdk`. The repo calls the SDK GA and lists v1.0.14; its releases also show v1.0.15 preview releases, including one on Sep 23. ([SDK repo](https://github.com/github/copilot-sdk), [releases](https://github.com/github/copilot-sdk/releases))

The SDK is a transport to the Copilot CLI/runtime, which runs the tool-use loop. Node, Python and .NET bundle or fetch the runtime; Go, Java and Rust normally expect a CLI installation, with some app-level bundling options. Rust also documents an in-process native-runtime mode. ([agent-loop architecture](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/agent-loop), [bundled CLI setup](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/bundled-cli), [Rust changelog](https://github.com/github/copilot-sdk/blob/main/CHANGELOG.md))

**CLI equivalence.** It uses the same Copilot runtime, tools and orchestration, but it is not a terminal-UI wrapper. SDK features include custom agents, subagents, tools, hooks, MCP, model selection and structured results. The compatibility guide distinguishes SDK-accessible capabilities from TUI-only features; do not assume every slash command or display feature is exposed. Sessions live in per-user state on the machine, and runtime versions should be pinned alongside the SDK. ([features](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features), [compatibility](https://docs.github.com/en/copilot/how-tos/copilot-sdk/troubleshooting/compatibility))

**Authentication and billing.** The SDK uses the local CLI’s stored sign-in by default, or can authenticate through user OAuth, supported environment tokens, server-to-server organization auth, or BYOK. GitHub documents SDK use with a Copilot subscription and says the default stored-user flow uses that user’s credentials. Its OAuth setup is designed for applications where users sign in with their own accounts. ([authentication](https://docs.github.com/en/copilot/how-tos/copilot-sdk/auth/authenticate), [GitHub OAuth setup](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/github-oauth))

Copilot Free, Pro, Pro+ and Max have monthly AI-credit allowances; GitHub counts third-party coding agents and Copilot CLI against AI credits, with one credit equal to $0.01. That makes the SDK’s subscription use metered by the plan’s AI-credit rules, rather than a separate SDK fee. ([individual billing](https://docs.github.com/en/copilot/concepts/billing-and-usage/individuals/billing), [plan comparison](https://docs.github.com/en/copilot/get-started/plans))

**VIA lifecycle and risks.** It supports create/resume, streaming typed events, wait/result, abort and status events. `immediate` messages steer the active turn before its next model call; `enqueue` runs after it. Usage docs describe token and AI-credit information. Many sessions can be created under a client, but concurrent capacity limits were **UNVERIFIED** in the sources reviewed. ([steering and queueing](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/steering-and-queueing), [usage and billing](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/usage-and-billing))

**Verdict:** Use the SDK where VIA needs structured session lifecycle control; its shared runtime and account-based billing fit VIA’s local, user-owned-account model.

## Cursor SDK, Python SDK and SDK Bridge

**Identity and runtime.** Cursor maintains `@cursor/sdk` and `cursor-sdk` for TypeScript and Python. Both are v1.0.32; PyPI records the Python release on Sep 22, 2026. The Python package is proprietary and explicitly marked public beta. The SDK Bridge is a Cursor-maintained public repository exposing the stable `sdk.v1` protocol; its visible latest GitHub release is v1.0.31, while the package registries show v1.0.32. **UNVERIFIED:** whether the matching v1.0.32 standalone Bridge release is published but not yet visible in the release listing. ([PyPI metadata](https://pypi.org/project/cursor-sdk/), [npm package](https://www.npmjs.com/package/%40cursor/sdk), [Bridge releases](https://github.com/cursor/sdk-bridge/releases))

The TypeScript SDK runs the local agent loop in the Node process or uses Cursor’s cloud runtime. The Python adapter launches a bundled `cursor-sdk-bridge` child process; the bridge embeds the TypeScript SDK, binds loopback, and speaks Connect/gRPC-Web over HTTP/1.1 to the adapter, then HTTPS to Cursor’s API. A new language can implement a Bridge client, but there are no official Go, Rust or Java packages listed as shipped SDKs. ([TypeScript SDK docs](https://cursor.com/docs/sdk/typescript), [Python SDK docs](https://cursor.com/docs/sdk/python), [Bridge overview and protocol](https://github.com/cursor/sdk-bridge/blob/main/docs/protocol.md))

**CLI equivalence and configuration.** Cursor describes the SDK as the same agent running in the IDE, CLI and web app. The SDK can do repository work locally or in a Cursor-hosted VM and supports built-in tools, custom tools, MCP, subagents, model selection, skills/rules through configured setting sources, and `.cursor/hooks.json`. Local mode uses a platform sandbox helper; by default, tool calls run without interactive approval unless auto-review is enabled. Some settings must be passed again on resume: inline MCP servers, tool restrictions and `systemPrompt` are not persisted; hooks are file-based, not callbacks. The SDK does not auto-discover credentials from a Cursor app install. Its SQLite/JSONL agent store is documented under `~/.cursor/sdk-agent-store`; **UNVERIFIED:** whether it shares sessions with the interactive CLI. ([TypeScript SDK docs](https://cursor.com/docs/sdk/typescript), [Python SDK docs](https://cursor.com/docs/sdk/python), [Bridge protocol](https://github.com/cursor/sdk-bridge/blob/main/docs/protocol.md))

**Authentication, billing and AUP.** SDK calls require a Cursor user or service-account API key; browser login can mint a key. Cursor says API-key usage follows the same pricing/request pools and privacy rules as IDE and Cloud Agents, and user keys bill to the user’s plan. ([TypeScript SDK authentication and billing](https://cursor.com/docs/sdk/typescript))

There is a direct policy conflict to resolve before VIA uses this route. Cursor’s AUP says it applies to consumers, developers and businesses “regardless of subscription tier or how the Service is accessed,” and prohibits: **“Accessing the Service through automated or non-human means, whether through a bot, script, or otherwise.”** The SDK is expressly for programmatic scripts and automation, but the current AUP gives no SDK exception. This applies to both personal local automation and a product offered to others; use of another person’s account/key would add a separate account-sharing issue. The Terms of Service incorporate the AUP, and the AUP controls on acceptable-use conflicts. ([AUP, last updated Aug 11, 2026](https://prod.cursor.com/en-US/acceptable-use-policy), [Terms, last updated Sep 3, 2026](https://cursor.com/terms-of-service))

**VIA lifecycle and risks.** It supports create/resume, list/get, streamed run events, wait/result, cancel, status and token usage. `run.steer()` only works for local foreground runs; cloud and detached runs return `revert_to_followup`. Cloud usage includes billing-pipeline cost; local billed cost is not available in the SDK docs. The Python wheel embeds a large per-platform Bridge binary; pin SDK, protocol and Bridge versions together. ([TypeScript SDK API](https://cursor.com/docs/sdk/typescript), [Python SDK API](https://cursor.com/docs/sdk/python), [version policy](https://github.com/cursor/sdk-bridge/blob/main/docs/versioning.md))

**Verdict:** The API and lifecycle are attractive, but do not adopt while the published AUP text remains in conflict with automated SDK use. Ask Cursor for a written exception that covers the intended use.

## Google Antigravity Python SDK

**Identity and runtime.** The official package is `google-antigravity`, maintained by Google, Apache-2.0, Alpha, version 0.1.18 released Sep 22, 2026. Its platform wheels total about 244 MB and contain the compiled runtime. ([PyPI package and release files](https://pypi.org/project/google-antigravity/), [official repo](https://github.com/google-antigravity/antigravity-sdk-python))

The Python code discovers and spawns the bundled Go `localharness` binary. It communicates over WebSockets using protobuf messages serialized as JSON; this is not the `agy` CLI binary. The SDK docs describe a stateful agent runtime with tool execution and context management, but I found no primary source confirming it uses the exact CLI agent configuration or full CLI runtime. ([connection implementation overview](https://github.com/google-antigravity/antigravity-sdk-python/blob/main/google/antigravity/connections/README.md), [SDK overview](https://www.antigravity.google/docs/sdk/overview))

**Capabilities and parity.** The SDK documents local file and command tools, custom Python tools, MCP, skills from specified paths, lifecycle hooks, policies and subagents. Its high-level `Agent` defaults to read-only; callers enable write capabilities explicitly. `system_instructions` is configurable. I found no documented promise that it automatically loads `AGENTS.md`, `GEMINI.md`, `agy` slash commands or the CLI’s project/user settings, and web/search-tool parity is **UNVERIFIED**. ([PyPI package documentation](https://pypi.org/project/google-antigravity/), [connection README](https://github.com/google-antigravity/antigravity-sdk-python/blob/main/google/antigravity/connections/README.md))

**Authentication and terms.** The SDK documents Gemini Developer API keys and Gemini Enterprise/Vertex API keys or Application Default Credentials; it does not document Google AI Pro/Ultra sign-in. Google’s Antigravity terms state: **“Using third party software, tools, or services to access the Service (e.g. using OpenClaw with Antigravity OAuth) is a breach of this Agreement.”** The FAQ directs third-party coding-agent users to a Gemini Enterprise or Google AI Studio API key. So an SDK API/Vertex route is a separate credentialed service path; using Antigravity personal OAuth from VIA is prohibited by the published text. ([SDK auth](https://www.antigravity.google/docs/sdk/overview), [Antigravity terms](https://antigravity.google/terms), [Antigravity FAQ](https://www.antigravity.google/docs/faq/))

**VIA lifecycle and risks.** The low-level connection API supports `send`, streamed `receive_steps`, `cancel`, `disconnect`, `is_idle` and `conversation_id`. SDK docs show stateful conversations, but I could not verify a durable resume/fork API, a mid-turn steer operation, or a structured final-result contract equivalent to VIA’s needs. Numeric usage/cost reporting is **UNVERIFIED**. The Go binary is bundled in platform wheels, so package updates can change the runtime without a separately installed CLI. ([connection API](https://github.com/google-antigravity/antigravity-sdk-python/blob/main/google/antigravity/connections/README.md), [SDK overview](https://pypi.org/project/google-antigravity/))

**Verdict:** Use only for an explicitly API-key, Vertex or local-model adapter. It is not a way to reuse a personal Antigravity subscription.

## Gemini CLI SDK and `@google/gemini-cli-core`

**Identity and runtime.** Google’s Gemini CLI monorepo contains a TypeScript package named `@google/gemini-cli-sdk`, licensed Apache-2.0. Its package source shows `0.61.0-nightly.20260908.gc647533d6`, depending on the sibling `@google/gemini-cli-core` workspace package. **UNVERIFIED:** whether a corresponding SDK package/version is published and installable from the public npm registry; the repository package name alone does not establish that. No official Python SDK was found. ([SDK package source](https://github.com/google-gemini/gemini-cli/blob/main/packages/sdk/package.json), [core package role](https://github.com/google-gemini/gemini-cli/blob/main/docs/core/index.md))

The SDK runs an in-process agent loop using Gemini CLI core and local tool execution; it does not spawn the Gemini CLI. The design document says the simple agent loads workspace and user settings and is equivalent to `gemini -p` for a basic prompt. It says advanced hooks, skills, subagents and ACP are missing, but later sections describe some skill/hook APIs. That internal inconsistency makes their current parity **UNVERIFIED** without checking the exact published artifact. ([SDK design](https://github.com/google-gemini/gemini-cli/blob/main/packages/sdk/SDK_DESIGN.md))

**Capabilities and auth.** Core owns model communication, tools and request processing. The design describes `GEMINI.md`-style system instructions, custom tools, sessions and resume; it does not provide a full CLI command surface. Current Gemini CLI terms list Google-account Gemini Code Assist, Gemini Developer API key and Vertex AI as CLI auth routes, but warn: **“Directly accessing the services powering Gemini CLI … using third-party software, tools, or services … is a violation of applicable terms and policies.”** Google announced that Gemini CLI stopped serving individual Google AI Pro, Ultra and free accounts on June 18, 2026; enterprise and API-key users were unaffected. Do not treat local OAuth credentials as permission for VIA to automate the service. ([terms and supported auth](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/tos-privacy.md), [June 18 transition announcement](https://github.com/google-gemini/gemini-cli/discussions/28017))

**VIA lifecycle and risks.** The design documents session start/resume, streaming chunks and custom tools. I found no confirmed SDK API for mid-turn steer, cancellation, status, concurrency guarantees or usage/cost reporting; these are **UNVERIFIED**. The CLI has a more established tool, configuration and ACP surface than the SDK design describes, but API-key or enterprise auth should be chosen to match the relevant terms. ([SDK design](https://github.com/google-gemini/gemini-cli/blob/main/packages/sdk/SDK_DESIGN.md), [CLI tool reference](https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/tools.md), [CLI configuration reference](https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/configuration.md))

**Verdict:** Prefer Gemini CLI headless or ACP for closer CLI behavior; use the SDK only when embedding core is a requirement and the exact installable package, lifecycle API and auth path have been verified.

## Meta Muse Code SDK

**Identity and runtime.** The SDK is Meta-maintained under `meta-models/muse-code-sdk`, MIT-licensed and in developer preview. Official packages are `@muse-code/sdk` (TypeScript; source package version 1.3.0) and `muse-code-sdk` (Python; v1.3.1, released Sep 21, 2026). Python also requires `muse-code-msp`. The SDK repo describes the API as pre-1.0/no stability promise, while current TypeScript source says 1.3.0; follow the current developer-preview notice, not the version number, for maturity. ([repo and preview status](https://github.com/meta-models/muse-code-sdk), [TypeScript package source](https://github.com/meta-models/muse-code-sdk/blob/main/clients/sdk-ts/package.json), [PyPI release](https://pypi.org/project/muse-code-sdk/))

The SDK spawns the user’s native `muse` executable with `serve` and communicates over stdio using the Muse Session Protocol. This is the same Muse Code host/runtime that powers the CLI, not a separate API agent loop. Official docs support TypeScript and Python; other languages can implement the protocol, but are not listed as official SDK packages. ([Meta SDK announcement](https://dev.meta.ai/resources/blog/muse-code-new-plans-and-features), [SDK quickstart](https://meta-models.github.io/muse-code-sdk/next/guides/quickstart/), [SDK repo](https://github.com/meta-models/muse-code-sdk))

**Capabilities and parity.** Muse Code prompts to trust a workspace, which loads its skills, rules and hooks. `muse serve` exposes the same session protocol to SDK clients. SDK calls can start, resume and fork sessions, stream items, answer permission requests, steer, interrupt/cancel, read/list session status and receive terminal outcomes. The host may hold multiple sessions, but one loaded session is leased to one host process at a time. ([Muse Code overview](https://dev.meta.ai/docs/muse-code), [session/turn model](https://meta-models.github.io/muse-code-sdk/next/guides/msp-concepts/sessions-and-turns/), [quickstart](https://meta-models.github.io/muse-code-sdk/next/guides/quickstart/))

Muse Code includes file and shell tools, skills, rules, hooks, MCP and subagents; the SDK is a client of that host, so it inherits host behavior and permission handling rather than reimplementing tools. I found no supported numeric token/cost reporting field in the reviewed SDK docs; mark it **UNVERIFIED**. SDK and host protocol fingerprints are version-coupled; Python deliberately fails initialization if the host fingerprint differs from its pin. ([Muse Code overview](https://dev.meta.ai/docs/muse-code), [compatibility policy](https://meta-models.github.io/muse-code-sdk/next/compatibility/), [SDK API reference](https://meta-models.github.io/muse-code-sdk/next/generated/sdk/session/))

**Authentication and subscription terms.** `muse serve` can use the CLI’s stored credential; `META_API_KEY` takes precedence. Meta documents API-key billing as pay-as-you-go and subscription billing as flat monthly usage through the CLI. Its subscription help says: **“Your subscription only works through the Muse Code CLI while signed in with your Meta Model API account.”** Meta’s API terms also restrict transferring keys to third parties. Because the SDK officially drives `muse serve`, subscription login appears technically reachable through that host, but whether an SDK-driven third-party wrapper counts as “through the CLI” for subscription entitlement is **UNVERIFIED**. A product must not share one user’s subscription credential with others; each user needs their own authorized sign-in or API key. ([auth and billing](https://dev.meta.ai/docs/muse-code/auth), [subscription help](https://dev.meta.ai/help/subscriptions/what-is-a-muse-code-subscription), [terms](https://dev.meta.ai/legal/terms-of-service))

**Verdict:** Best fit for VIA’s resume, steer, cancel, status and result verbs because it controls the real Muse Code host through a versioned protocol. Pin and check the installed `muse` host version, and clarify subscription entitlement before relying on it.
