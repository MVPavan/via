# Goose research — v1.52.0

**Research date: 2026-09-24.** Goose is not installed in this environment (`goose` was not found on PATH), so I could not run local `--help` or verify runtime behavior. Flags and contracts below come from the current Goose docs/source and ACP registry, not a local binary. Claims whose behavior those sources don’t establish are marked **UNVERIFIED**.

## 1. Identity

Goose is an open-source coding and general-purpose agent maintained in the `aaif-goose/goose` repository, which identifies it as part of the Linux Foundation’s Agentic AI Foundation. Its license is Apache-2.0. The current release and ACP registry entry are **v1.52.0**, released **2026-09-23**. Recent tags include 1.50.1, 1.51.0, and 1.52.0; releases are frequent, but I did not establish a fixed release schedule. ([repository README and license](https://github.com/aaif-goose/goose/tree/main), [v1.52.0 release, 2026-09-23](https://github.com/aaif-goose/goose/releases/tag/v1.52.0), [ACP registry, read 2026-09-24](https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json))

Install options include the vendor’s CLI script, Homebrew, and ACP-registry installation by supported clients. The repository’s CLI install command is `curl -fsSL https://github.com/aaif-goose/goose/releases/download/stable/download_cli.sh | bash`; the ACP registry pins Goose’s launch command to the `v1.52.0` binary followed by `acp`. ([installation docs, current 2026-09-24](https://goose-docs.ai/docs/getting-started/installation/), [ACP registry, read 2026-09-24](https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json))

## 2. Auth and billing

Goose supports provider API keys and subscription-backed integrations. Its current docs recommend ACP providers for using existing Claude Code or ChatGPT Plus/Pro subscriptions; Goose lists `claude-acp` and `codex-acp` and describes their adapter installation and authentication prerequisites. ([ACP provider guide, current 2026-09-24](https://goose-docs.ai/docs/guides/acp-providers/), [provider setup guide, current 2026-09-24](https://goose-docs.ai/docs/getting-started/providers/))

The vendor material supports those as intended Goose integrations. For Claude, Anthropic says Pro/Max plans include Claude Code, and its consumer terms apply to those plans “including when they use Claude Code.” For OpenAI, its help page says ChatGPT terms apply when a user signs in to Codex. I found **no explicit statement in the reviewed vendor terms that either grants or categorically forbids using a personal subscription through Goose’s third-party ACP integration**. Treat that specific terms question as **UNVERIFIED**; users remain subject to their provider’s account limits and terms. ([Anthropic Claude Code setup, current docs](https://docs.anthropic.com/en/docs/claude-code/getting-started), [Anthropic consumer-terms update, 2025-08-28](https://www.anthropic.com/news/updates-to-our-consumer-terms), [OpenAI Codex plan FAQ, read 2026-09-24](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan))

## 3. Headless CLI contract

The headless command is `goose run`. It accepts `--text`, `--instructions FILE` (or `-` for stdin), and `--recipe FILE` with repeated `--params KEY=VALUE`; `--system TEXT` adds system instructions. The docs also list `--resume`, `--session-id`, `--no-session`, `--provider`, `--model`, `--max-turns`, and `--output-format`. ([CLI reference, current main source/docs read 2026-09-24](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/goose-cli-commands.md), [CLI argument definitions, current main](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/cli.rs))

- **Output formats:** `text` (default), `json`, and `stream-json`. Goose’s source defines JSON output as `{messages, metadata}`; metadata fields include `status`, token totals, cached input tokens, and optional `cost_usd`. The final response is represented within `messages`, not a dedicated `final_text` field. ([CLI arguments](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/cli.rs), [JSON/stream event types](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/session/mod.rs))
- **Stream events:** source defines `message`, `notification`, `error`, and `complete` event types. Message events wrap a Goose message; notifications carry `extension_id` and flattened log/progress data; completion carries token and cost fields. **UNVERIFIED:** the exact serialized message content schema and exact `metadata.status` values are not fully specified as a public CLI schema. ([Goose CLI source, current main](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/session/mod.rs))
- **Session ID in output:** the JSON/stream event structs shown in current source do not include a session ID. Use `--session-id` when supplying one, or query/export the saved session separately. Whether every text-mode path prints the generated ID is **UNVERIFIED** from the reviewed source/docs. ([Goose CLI source, current main](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/session/mod.rs), [session CLI options](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/goose-cli-commands.md))
- **Exit/errors:** stream output has an `error` event; Goose’s headless tutorial tells scripts to check process exit codes. **UNVERIFIED:** documented exact exit-code mapping for provider errors, tool errors, and interrupted turns. ([Goose CLI source](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/session/mod.rs), [headless tutorial, current 2026-09-24](https://goose-docs.ai/docs/tutorials/headless-goose/))
- **Model and reasoning:** `--provider` and `--model` override provider/model selection; defaults also come from Goose configuration and `GOOSE_PROVIDER` / `GOOSE_MODEL`. I found no native `goose run --effort` flag; reasoning effort is provider/model-specific and **UNVERIFIED** as a general Goose CLI control. ([CLI argument definitions](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/cli.rs), [configuration docs, current 2026-09-24](https://goose-docs.ai/docs/guides/config-files/))
- **Role/system prompt:** use `--system` for additional instructions, or a recipe that carries prompt/configuration. This is prompt injection, not a documented named “role” or agent-profile selector. ([CLI reference](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/goose-cli-commands.md), [recipes guide, current 2026-09-24](https://goose-docs.ai/docs/guides/recipes/))
- **Permissions and sandbox:** `GOOSE_MODE` supports `auto`, `approve`, `smart_approve`, and `chat`; Goose docs say autonomous mode is the default. Tool-level permissions can allow, ask, or deny. `--container` runs extensions in Docker; I found no general Goose workspace sandbox or `--add-dir` flag for `goose run`. ([permission modes, current 2026-09-24](https://goose-docs.ai/docs/guides/managing-tools/goose-permissions/), [CLI flags](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/cli.rs))
- **Working directory / extra directories:** CLI session creation uses the process current directory. I found no CLI option for extra workspace directories; **UNVERIFIED** whether other configuration mechanisms can establish them. ([CLI source, current main](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/cli.rs))
- **Stdin and first run:** `--instructions -` reads stdin. Goose’s headless guide recommends preconfiguring provider settings, setting `GOOSE_MODE=auto`, and disabling generated session naming to avoid its extra background model call. Provider setup/authentication may require interactive or browser login beforehand. No Goose-specific project-trust dialog is documented in the reviewed headless guide. ([CLI docs](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/goose-cli-commands.md), [headless tutorial](https://goose-docs.ai/docs/tutorials/headless-goose/), [subscription integration guide](https://goose-docs.ai/blog/2026/03/19/use-goose-with-your-ai-subscription/))
- **Structured output and timeout:** `json`/`stream-json` structure the *envelope*, but I found no CLI JSON-schema-constrained response option. I found no wall-clock timeout flag for `goose run`; `--max-turns` bounds agent iterations, not elapsed time. Both absences are **UNVERIFIED** beyond the reviewed current CLI option list. ([CLI argument definitions](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/cli.rs))

## 4. Session lifecycle in the CLI

`goose run --resume --session-id ID` resumes a specific session; `--resume` without an identifier selects the most recent user session. Current source returns errors for missing sessions or invalid identifiers rather than silently creating a new one. Session commands also support `--fork` (with `--resume`) to duplicate history. Sessions use SQLite (`sessions.db`) since Goose 1.10.0; `goose session list --format json` and `goose session export --format json` provide query/export paths. ([CLI source](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/cli.rs), [session docs](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/goose-cli-commands.md))

I found no documented mid-turn steering or background-run mode for `goose run`. `--interactive` continues into a user-facing session; it is not a headless async job interface. Cancellation is available through process signals, but Goose’s CLI docs do not define a special cancel command or guarantee graceful signal semantics; exact cleanup behavior is **UNVERIFIED**. ([CLI reference](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/goose-cli-commands.md))

## 5. Other programmatic surfaces

- **ACP:** `goose acp` serves the agent over stdio. `goose serve` offers ACP over HTTP/WebSocket at `/acp` (default `127.0.0.1:3284`) and uses `GOOSE_SERVER__SECRET_KEY`; the HTTP/WebSocket route adds transport auth. ([ACP setup, current 2026-09-24](https://goose-docs.ai/docs/gdk/acp/), [CLI command reference](https://goose-docs.ai/docs/guides/goose-cli-commands/))
- **SDK:** Goose’s GDK SDK is alpha and exposes the provider layer in Rust, Python, and Kotlin for streaming/completion, tools, usage, and compaction. It is a model/provider API, not a drop-in wrapper for the entire Goose agent session lifecycle. ([GDK SDK docs, current 2026-09-24](https://goose-docs.ai/docs/gdk/sdk/), [API reference v0.1.0-alpha.6](https://goose-docs.ai/docs/gdk/api-reference/?language=rust&version=0.1))
- **MCP:** `goose mcp <name>` runs an enabled bundled MCP server. It exposes Goose tools as MCP servers; it is not the programmatic agent-session API. ([CLI reference](https://goose-docs.ai/docs/guides/goose-cli-commands/))
- **Legacy server:** Older Goose architecture included a separate `goosed` REST/SSE API. Current docs identify `goose serve` as the ACP HTTP/WebSocket path; don’t assume the older API applies to v1.52.0. ([Goose architecture post, 2026-04-08](https://goose-docs.ai/blog/2026/04/08/goose-acp-and-new-tui/), [current ACP setup](https://goose-docs.ai/docs/gdk/acp/))

## 6. ACP support

Goose is a **native ACP agent**, not merely an adapter around another agent. The current ACP registry entry is `goose`, version **1.52.0**, Apache-2.0; it launches the packaged binary with `acp`. The project documentation says `goose acp` uses stdio and the client owns the subprocess lifecycle. ([ACP registry, read 2026-09-24](https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json), [Goose ACP guide, current 2026-09-24](https://goose-docs.ai/docs/gdk/acp/))

Goose documents standard session creation, loading, prompting, cancellation, and listing. The ACP session ID is returned by session creation. It reports streaming updates; Goose’s ACP reference documents usage data (input/output/total tokens, cache tokens, cost) and per-message/session usage updates. ([Goose custom distro ACP notes, current main](https://github.com/aaif-goose/goose/blob/main/CUSTOM_DISTROS.md), [ACP reference, current 2026-09-24](https://goose-docs.ai/docs/gdk/acp/reference/))

Model/provider defaults come from Goose config or environment (`GOOSE_PROVIDER`, `GOOSE_MODEL`). Mode is controlled by Goose configuration; Goose’s ACP reference includes an unstable mode/config-setting API and an unstable system-prompt set/append API. That prompt method can add a role prompt after session creation, but VIA must version-gate these Goose-specific extensions. Goose has a documented unstable `_goose/unstable/session/steer` method for adding input to an active prompt. ([Zed setup guide, current 2026-09-24](https://goose-docs.ai/docs/gdk/acp/zed/), [ACP reference](https://goose-docs.ai/docs/gdk/acp/reference/))

ACP uses the provider credentials already configured for Goose. Stdio is local and has no separate transport secret in the documented launch flow; `goose serve` uses a secret key for HTTP/WebSocket. I found no evidence that the ACP handshake itself performs subscription login. ([ACP setup](https://goose-docs.ai/docs/gdk/acp/), [subscription-backed provider guide](https://goose-docs.ai/docs/guides/acp-providers/))

Goose’s ACP reference contains many **unstable** Goose-specific methods. Standard ACP can give VIA session lifecycle and result streaming, but Goose’s documented steering and system-prompt mutation are extensions, not portable ACP guarantees. ACP session recipes are another gap: Goose issue #7596 documents that `session/new` had no recipe field or recipe-application equivalent; CLI `goose run --recipe` remains the route for recipes. ([ACP reference](https://goose-docs.ai/docs/gdk/acp/reference/), [recipe/ACP issue #7596, opened 2026-03-01](https://github.com/aaif-goose/goose/issues/7596))

A Goose ACP fork/replay issue (#9460, opened **2026-05-28**) remains open in the repository; it concerns fork behavior and should not be read as proof that basic `session/load` is broken. Session-load failures and connection closures have also been reported; issue #10535 is closed, but the report is a reminder to test resume against the pinned Goose release. ([issue #9460](https://github.com/aaif-goose/goose/issues/9460), [issue #10535](https://github.com/aaif-goose/goose/issues/10535))

## 8. Automation pitfalls

- **Subscription limits and login:** subscription-backed ACP providers require their provider CLI/account to be authenticated first, and those plans have their own limits. Goose documents using existing subscriptions; it does not remove provider-side caps. ([Goose ACP providers](https://goose-docs.ai/docs/guides/acp-providers/), [Anthropic Pro/Max help, current](https://support.anthropic.com/en/articles/11145838-using-claude-code-with-your-pro-plan))
- **Unexpected extra inference:** session naming can make an extra model call; Goose’s headless guide recommends `GOOSE_DISABLE_SESSION_NAMING=true` to avoid it. ([Headless tutorial](https://goose-docs.ai/docs/tutorials/headless-goose/))
- **Approval hangs:** autonomous mode is the documented default; manual and smart approval require decisions. For unattended operation, choose and document a mode explicitly, plus tool permissions. ([Permission modes](https://goose-docs.ai/docs/guides/managing-tools/goose-permissions/))
- **Extension failures:** Goose sessions load configured extensions; a failed or blocked extension can affect execution. Test required extensions and timeouts with the exact deployed config. ([CLI source](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/cli.rs))
- **Output/version drift:** `stream-json` is defined by Rust source types rather than a complete stable CLI schema. Pin Goose and contract-test event parsing; don’t infer final text from one observed message layout. ([Goose CLI output types](https://github.com/aaif-goose/goose/blob/main/crates/goose-cli/src/session/mod.rs), [releases](https://github.com/aaif-goose/goose/releases))
- **Resume and fork:** basic resume is available, but session-load failure reports exist, and ACP fork replay has an open report. Test the exact lifecycle VIA exposes. ([issue #10535](https://github.com/aaif-goose/goose/issues/10535), [issue #9460](https://github.com/aaif-goose/goose/issues/9460))
- **Stdin:** instructions can come from stdin via `--instructions -`; recipe/prompt modes avoid depending on stdin behavior. Goose’s docs do not specify EOF or conflicting-input precedence, so those are **UNVERIFIED**. ([CLI reference](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/goose-cli-commands.md))

## 9. Recommendation

For a VIA Goose adapter, use **`goose acp` over stdio** as the primary route. It gives VIA a real Goose session ID, streaming result updates, standard resume/cancel, and usage reporting, while allowing the adapter to declare Goose’s steer and system-prompt mutation as version-gated extensions. Add a `goose run --output-format json` fallback for one-shot recipe or prompt runs, where its `messages` and token/cost metadata are useful. Do not claim stable steer, recipe-backed ACP sessions, effort selection, or wall-clock timeout until each is verified against a pinned release. ([ACP setup](https://goose-docs.ai/docs/gdk/acp/), [ACP reference](https://goose-docs.ai/docs/gdk/acp/reference/), [CLI reference](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/goose-cli-commands.md))
