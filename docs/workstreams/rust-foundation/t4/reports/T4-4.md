## Choices where the design left room

1. **Step-row failure site.** A known `NotCommitted` on a step row records
   `FailureSite::Event` and carries the row into the `failed(store)`
   terminal; an uncertain outcome latches and does not carry the row
   (§3.2).
2. **Seam placement.** `store.commit.step` is hit on the client side of
   `commit_steps`, so a scenario can fail or pause one row by hit number.
   Step rows do not get a `core.commit.before_send` hit; scenarios use
   `store.commit.step` instead.
3. **Row times.** A row's `started_ms`/`ended_ms` come from the marks' `at`
   (Adapter arrival) through the tracker's `Clock` (monotonic base plus the
   wall time at acceptance), not from a wall read at fold time.
4. **Boundary at step 0.** A model mark after tool results is a boundary
   only once the turn is accepted (`current >= 1`), so no row has step 0.
5. **`tokens`** is `null` before the first sample; with samples it is
   labelled with the fake's declared scope, `"unavailable"`
   (`FAKE_TOKEN_SCOPE`, shared with `capabilities`).
6. **Lost-reply event** in the Store-failure scenarios where the design asks
   for an unknown head: a caller cancel (`cancel.requested`), the one
   non-terminal durable event a scenario can trigger once text is gone.
7. **Eviction** in `s1_c1_status_every_member_after_eviction_and_restart`
   is shown by `daemon/status` reporting no active and no in-use slots
   before the `status` read.

## Concerns and limits

1. **Byte budget coverage.** No end-to-end test fills the 4 MiB
   observation budget any more; the unit test covers the delivery path
   only. It returns end to end when a route can build items near 1 MiB
   (Codex usage keys or a vendor with longer fields).
2. **Token scope label.** C1 §3.7 says `tokens` is `null` when the route
   has no validated source. The fake declares `usage.tokens:
   "unavailable"` yet its `usage` message is exact by construction (§2.5),
   so `status` shows numbers labelled `"unavailable"`. The design's test
   row says "the fake's declared scope", which this follows. The
   coordinator may want the fake's declared scope changed (a
   capabilities decision, outside this chunk).
3. **The test name** `s1_f24_observation_budget_..._or_4_mib` still names
   the byte bound its body no longer checks; it is kept because the plan's
   test table names it.
4. **Timing in F24/F27 and the unknown-flood test.** They wait for
   `last_activity_at` to hold still across two reads 100 ms apart before
   the next burst. This is event-based pacing (the activity clock), but a
   Route delayed by more than 100 ms between messages would release the
   burst early; the Wire queue would then overflow and the test would fail
   rather than pass wrongly.
5. The commit-check build left a `target/commitcheck` directory in the
   worktree's (gitignored) `target/`.

### Finding 1: the fake's token scope and the envelope's `usage`

Decision: the fake declares `capabilities.usage.tokens = "turn"`.

- `FAKE_TOKEN_SCOPE` is now `"turn"` (`crates/via-core/src/api.rs`). It
  labels the receipt's capabilities, `status` `progress.tokens.scope` and
  the envelope's `usage.scope`.
- The new `Usage::fake(total)` fills `total_tokens` with scope `turn` and
  provenance `reported` when the turn had at least one sample. Without a
  sample it is `Usage::UNAVAILABLE`, and the other counts stay `null`.
  `terminal_envelope` now takes the `usage` value as a parameter.
- The drive passes `StepTracker::turn_tokens()`: completed steps plus the
  open step, which equals the sum of the turn's step rows.
- Resolution of a never-submitted turn and crash recovery pass
  `Usage::UNAVAILABLE`, since a crashed daemon's samples are gone. A
  recovered turn's envelope therefore does not report the total of the
  rows committed before the crash.
- `s1_progress_tokens_sum_per_step_and_label_scope` now also checks that
  the receipt's scope is `"turn"` and that the envelope's `usage` is
  exactly `{…null, "total_tokens": Σ rows, "scope": "turn", "provenance":
  "reported"}`, with Σ rows = 170. No other test or snapshot checked the
  fake's scope. `s1_prompt_to_result.rs` still asserts `unavailable` usage
  for its turn, which has no sample.

### Finding 2: token counts Store cannot represent

- `StepTracker::fold` returns `Result<Folded, Unrepresentable>`.
  - Before any change it computes the step's usage after the item: past
    the boundary, if the item has one.
  - It uses checked addition for the keyless fold, the step sum and the
    turn sum, and refuses any of them past `TOKENS_MAX = i64::MAX`, which
    also covers a single sample of 2^63.
  - A refused item changes nothing, so no row is built from it. Every
    accepted fold keeps the turn's sum representable, so the rows the
    terminal carries and the envelope's total always fit.
  - The tracker records the refusal (`unrepresentable()`).
- The run loop's `stop_for_store` also issues a stop with the new cause
  `StopCause::Protocol` (`StopSpec::Protocol`, timed as `Store`: force now),
  once per turn (`Control.refused`).
  - `attach` lets `protocol` override any cause but `store`.
  - `dispose` fails the turn `protocol` under that order in every row
    where `store` fails `store`.
  - An item refused after `execute` returned, when no order can attach,
    gets the same failure after `dispose`. A Store failure still takes
    precedence.
  - Like Core's idle order, the order is observed with `cancel.requested`
    and settles a `cancel` outcome.
- Tests:
  - Unit test `unrepresentable_tokens_are_refused_before_any_row`. A
    sample of 2^63 is refused. A second key that would overflow the step
    sum is refused. Output after results with a sample that takes the turn
    past `i64::MAX` is refused without building step 1's row, while the
    same boundary without the sample still folds.
    `usage_supersedes_within_a_key_and_adds_across_keys` also checks
    `turn_tokens()`.
  - Daemon test `s1_progress_unrepresentable_tokens_fail_protocol`, with a
    vendor that hangs:
    - a `usage` sample of 2^63 fails the turn `protocol`, `turn.ended` is
      the last event and the rows are `[(1, null)]`;
    - a sample that takes the turn's sum past `i64::MAX` fails the same
      way, with rows `[(1, i64::MAX), (2, null)]`.

## Review round 2 fixes

Round 2 (Sol high) accepted both round 1 fixes and the new
`StopCause::Protocol`. It found one important gap: `forced_terminal`
(`crates/via-core/src/engine/stop.rs`) handled idle and store failures
but not a refused token count. If the daemon forced Route before the
`protocol` stop completed, the turn was committed `cancelled` or
`unknown`. The fix is in commit `4d3ae75`.

- `forced_terminal` fails the turn `protocol` when either of these holds:
  the handed-off order's cause is `Protocol` (`ForcedTurn.cause`, the same
  way the idle order reaches this function), or the carried record's
  tracker refused a sample (`record.steps.unrepresentable()`, the same way
  the store failure reaches it through `record.first_failure`). The
  second case covers a refusal made after Route ended under the force.
- Precedence, in line with the run loop's disposition: the check runs
  after the idle row and before the store row. So `protocol` overrides
  idle and cancel, and `store` still wins.
- Test: `s1_progress_unrepresentable_tokens_survive_a_forced_stop`.
  - Core is held at `core.observations.pause` #3, on the 2^63 sample. The
    daemon force-stops, the test waits until Route has closed the vendor,
    then releases Core. Core refuses the sample and issues its `protocol`
    order after the force, and the turn is handed to final shutdown.
  - The test asserts that the committed turn is `failed` with
    `failure.class = protocol` and that exactly one `turn.ended` exists.
  - This test holds Core before the refusal rather than holding the stop
    after it. The `protocol` order is force-now, and Route has no seam
    that holds a stop in progress, so this order of events is the one
    that can be produced reliably. Both orders of events reach
    `forced_terminal` with the refusal recorded.
  - RED (`r2-red-cli.log`): `failed(protocol) 0, turn.ended 1`; the
    envelope was `cancelled` with `cancel.outcome = forced`.
  - GREEN (`r2-green-cli.log`): the test passes, and it passed 5 of 5
    repeated runs.
