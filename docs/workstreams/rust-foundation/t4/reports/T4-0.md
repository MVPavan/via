### 1.4 Inventory corrections [t4r1.18]

Round 1's inventory carried three statements that round 2 corrects or scopes.

| Round-1 statement | Correction |
|---|---|
| "Whether every event kind carries a `turn` field" was listed as unverified [I]. | [V] Events carry a **nullable** `turn`: every Core event has an optional `turn` (`crates/via-core/src/api.rs:1341`); session-level events have none. `events.turn` is a nullable column with a deferred composite foreign key to `turns` (design §3.7). The [I] tag is dropped. |
| "The `at` timestamp is fixed-width UTC, so string order is time order" was listed as unverified. | `at` is fixed-width UTC for ordinary dates (`rfc3339`, `api.rs:1361-1388` [V]), but it is a wall-clock string that Store does not validate and that can move backwards: **its order is not a commit order**. No design section relies on string order of `at`; Store parses it to milliseconds, refuses a malformed value, and orders by `seq`, `stamp` and those integers (design §3.7). |
| "Every event-commit writer routes through `Head`" was carried as an assumption. | False for the initial spawn event: `receipt.rs:120-133` builds it and `commit_spawn` inserts it (`sql.rs:590`) with no `Head`. It holds for **post-spawn commits**; the writers are listed in design §3.7 and the slice greps every `insert_event` reach. |
| Spawn was assumed to freeze `cwd` and `allow_untested`. | Not frozen: `receipt.rs:135-147` stores only `harness` and `model`. They become `params` keys (A14). |

### 10.2 Choices and deviations, with reasons

- **Decision 3, both forms, by buffer.** Per-connection buffers use up-front
  capacity: the 1 MiB stdout assembly buffer and five 96 KiB stdin pieces.
  So do replies and Store pages. The C1 line uses fixed charged 64 KiB
  segments. Up-front capacity there would be 32 sockets × 16 MiB = 512 MiB.
- **Decision 3 needed two more mechanisms.** serde_json's scratch `Vec` is
  internal and grows by doubling. It cannot be pre-sized, so it would still
  hold old and new allocations for every escaped string. Round 6 removes it
  from the value path:
  - peer-fed strings are `JsonStr` (a borrowed `RawValue`), unescaped once
    into an exact `String`;
  - the structure check is a non-allocating byte scanner;
  - an escaped object key is capped at 4 KiB, a new contract limit (A35,
    Q-R5-12).

  Without these, a maximal C1 request peaks near 100 MiB, and the sum at
  maximum counts does not fit 128 MiB. With them it peaks at about
  34.2 MiB, which fits the 36 MiB dynamic partition beside 4 drives of
  13 MiB, 32 MiB of staging and the 8 MiB Store partition. No count is
  lowered.
- **Decision 5 needs a stop cause.** "Order cleanup immediately through turn
  control" cannot use the stall's hop close. The overrun is Core's to detect,
  and the Adapter may never send again. A34 therefore adds
  `StopCause::Overflow`, a T3 amendment, used only for this. A19's stall
  stop order stays withdrawn.
- **Decision 2's guarantee is scoped to the turn's own terminal.** "A
  committed `turn.ended` implies all rows are durable" holds for a
  `turn.ended` written by the turn's drive: its natural, forced or
  `failed(store)` terminal. It cannot hold for a terminal that recovery
  synthesizes after a crash, or that the Latch batch writes after an
  uncertain outcome, because an in-flight row may be lost. The design states
  the claim exactly that way.
- **Decision 6 keeps a text prefix.** The summary keeps a 128 KiB prefix of
  `final_text` instead of clearing it, recorded in `truncation` like the
  lists. The decision did not say; a prefix is more useful and stays inside
  the budget.
- **Decision 7 can drop a span under pressure.** When 64 spans are pending
  and a commit is in flight, a new span is dropped. Its units become
  unserved, never misattributed, so D4 holds. The alternative, making Route
  wait on the Store, would stall ingest.
- **Decision 11 adds one atomic.** A per-turn `AtomicU64` carries
  `last_activity_at`, because unknown messages no longer send an observation
  that could carry it. It holds no data and cannot queue.

### 11.2 Choices and deviations, with reasons

- **Decision 4: final text accumulates in Core.** Metering "as for denied and
  declined entries" needs one owner for the meter and the stop, and Core
  already owns both. So a route whose final text spans messages (Codex,
  OpenCode) sends it as a new internal observation, `final_text {key, text,
  replace}`. A present `turn.vendor_terminal.final_text` replaces it. Core
  keeps all accumulated members encoded in one up-front 1 MiB arena per
  turn. A replacement moves bytes in place (`copy_within`) and never
  allocates. Codex's delta-then-completed rule is unchanged; only where it
  runs moves. This amends C2 §4 (A29). It also narrows the 256 KiB payload
  rule to durable event payloads: a `final_text` piece is bounded by its
  vendor message (1 MiB) and by the meter.
- **Decision 2: no admission count lowered.** The arena replaces separate
  list and text buffers, so the drive reserve falls from 13 to 11.5 MiB. The
  sum is Store 8 + SQLite 8 + staging 32 + drives 46 + dynamic 34 = 128.
  To fit a maximal C1 request in 34 MiB, the per-node charge falls from
  32 B to 24 B. The largest retained value per node is one `String` or `Vec`
  header. This is still marked inferred; the margin is 368 KiB. Only one
  SQLite connection is long-lived; the read-only probe at open is dropped
  first.
- **Decision 3 adds turn holds.** With the stated coarse bound, one terminal
  carrying 1,029 rows reserves about 6.7 MiB, so four cannot be proved
  inside a shared 16 MiB. Instead, each submission reserves an 8 MiB hold
  (`TURN_DISK`) for its turn's terminal and lifecycle events, released by
  that terminal. At most 4 exist. The 16 MiB reserve then serves only the
  Latch batch's queued cancellations and recovery's terminals, 4.8 MiB, with
  the rest as slack for overshoot. Two consequences:
  - A session close and a queued turn's cancellation outside the Latch batch
    become ordinary writes; they were lifecycle in round 6. At the quota
    they are `store_error` `not_committed` and change nothing.
  - The WAL is charged a fixed 40 MiB, from runtime §6's 32 MiB admission
    stop plus one transaction, rather than per command.
- **Decision 10: backpressure, then a visible failure.** Route keeps two
  batches of 64 spans. When both are full it waits for the commit and reads
  no messages; a slow Store then fails the connection through the Wire
  queue, which is visible. A refused batch fails the connection as a raw-log
  failure. The `logs` result gains `incomplete`, read through a new
  `(session_id, type)` events index.
- **Decision 8 as decided.** The Latch batch after an uncertain outcome
  carries no rows and makes no completeness claim. Recovery makes none
  either.
- **Decision 9: every end counts.** An unknown or duplicate end also sets
  `results_since_output`; at worst a step boundary comes one model output
  early, never late.

  policy keeps runtime §6's checkpoint sentence; `WAL_MAX` (64 MiB) is the

- **Per-session connections.** A turn's span is the connection's durable end
  when `turn.submitted` commits and when its terminal commits. Bytes staged
  but not yet durable at either commit fall outside the turn's span and are
  returned to the session address only. This is the coarse form decision 3
  asks for.

### 14.2 Choices and deviations, with reasons

- **The WAL bound is loose.** It assumes a rebalance at every level for
  every entry write. With defaults and `h` ≤ 6 it is about 73 MiB for a
  maximal event batch; a terminal adds two entries per carried row. A tighter
  bound would need B-tree fill guarantees that SQLite does not give. The
  disk test records the measured growth, and `via-d9o.2.3` can replace the
  figure with a measured one. The SQLite facts were read in the bundled
  source (SQLite 3.53.2 in `libsqlite3-sys` 0.38.2): a page the transaction
  already wrote is overwritten, not appended; a rebalance involves three
  siblings and at most five pages; each WAL entry has a 24 B header and the
  WAL a 32 B header.
- **`codex_shared` is outside the pool floor.** It is charged only while a
  shared Codex server runs, which S1 does not do. Adding it to the floor
  would push the default floor to 129 MiB, above the 128 MiB default. It is
  bounded above by the pool less the lanes and the cache.
- **Some minimums equal their defaults** (`request_multiplier` 4,
  `request_nodes` 2 MiB, `reply_small` 64 KiB). Each default is the derived
  minimum of its class, so these keys can only be raised.
- **`sqlite_cache` has a 1 MiB minimum [I]**, because it is not a buffer
  with a maximal input. SQLite works with a smaller cache.
- **Session owner.** The per-session server's Route owns the `WireParts`
  until server or session close. A turn end that must stop the server
  (force close, Route failure, latch) closes it through that owner.
