# Verdict: UNSOUND

This is a document review at `98b2741`, not a review of implemented Task 4 behavior. The round-16 design adopts the owner’s main decisions: no raw log or memory pool, an admission floor, `via.log`, uncapped stderr, one-second `wait` polling, vendor `steps`, and file-backed final text. The findings below concern guarantees that the written mechanisms do not yet support.

## Blockers

1. **A disk-floor check prevents a valid keyed replay.** **Verified:** The design checks the floor before prompt-file copying and key lookup (`docs/workstreams/rust-foundation/t4/design.md:516`, `docs/workstreams/rust-foundation/t4/design.md:1079`). The runtime contract requires replay lookup before current admission checks (`docs/specs/runtime-contracts.md:727`). **Inference:** After a receipt is committed, an identical retry below the floor returns `admission_refused` instead of that receipt. **Smallest fix:** look up an existing key first; for a prompt-file retry, stream its identity for comparison without creating a new blob, then apply the floor to genuinely new work.

2. **The WAL can grow by more than one transaction past `wal.max`.** **Verified:** Running turns’ step-row commits continue while `wal_full` is set, yet the design and proposed runtime amendment say overshoot is at most one transaction (`docs/workstreams/rust-foundation/t4/design.md:558`, `docs/workstreams/rust-foundation/t4/design.md:1512`). **Inference:** A reader holding a WAL snapshot while a running turn completes many steps permits repeated commits and continued growth; disk exhaustion can then prevent the terminal commit. **Smallest fix:** reconcile the bound with the owner’s step-row decision. At minimum, state that `wal.max` is a soft threshold during admitted turns and remove the one-transaction guarantee; a hard bound needs a defined policy for those later commits.

3. **A committed envelope can point to a final-text file lost in a crash.** **Verified:** The design syncs `final_text.txt` before the terminal, but specifies no sync of its newly created directory entry or parent evidence directories (`docs/workstreams/rust-foundation/t4/design.md:689`, `docs/workstreams/rust-foundation/t4/design.md:830`); its blob protocol explicitly syncs the file *and* directory (`docs/workstreams/rust-foundation/t4/design.md:712`). **Inference:** A crash can leave the durable envelope’s only answer path missing. A partial write error can also leave a file ending inside a UTF-8 character while the turn is marked completed and truncated. **Smallest fix:** make the final-text path durable before terminal commit, define how sync failure affects the terminal, and trim a partially written file to a valid UTF-8 boundary before reporting its byte count.

## Important findings

4. **The `status` snapshot ordering is not secured.** **Verified:** A step row is committed at its boundary, while progress is published separately; `status` reads Store first and memory second, then claims progress is at least as new as the rows (`docs/workstreams/rust-foundation/t4/design.md:213`, `docs/workstreams/rust-foundation/t4/design.md:323`, `docs/workstreams/rust-foundation/t4/design.md:384`). **Inference:** If publication follows the row commit, a concurrent call can return that row with the previous `current_step`, contradicting the stated open-step rule. **Smallest fix:** specify and test publication before the boundary commit, or weaken the cross-source consistency claim and define the permitted skew.

5. **The raw-log removal leaves live S1 contract and test instructions behind.** **Verified:** A41 voids T3’s raw-failure row but does not address T3’s raw-incompleteness recovery procedure and raw-failure test (`docs/workstreams/rust-foundation/t4/design.md:1485`, `docs/workstreams/rust-foundation/t3/design.md:1513`, `docs/workstreams/rust-foundation/t3/design.md:1754`). Its amendment list also leaves the runtime fake-route sketch’s `RouteMessage.raw_ref` in place (`docs/specs/runtime-contracts.md:142`). These are executable contract and test directions, unlike the historical D4 record. **Smallest fix:** add explicit amendment dispositions for those T3 recovery/test passages and the runtime sketch.

6. **The `list` cursor guarantee fails when retention deletes session rows.** **Verified:** `ord` is allocated with `MAX(ord)+1`, while A38 promises that sessions created after page one never appear; the design itself notes that `ord` stops increasing strictly after deletion (`docs/workstreams/rust-foundation/t4/design.md:741`, `docs/workstreams/rust-foundation/t4/design.md:782`, `docs/workstreams/rust-foundation/t4/design.md:1667`). **Inference:** After retention removes the highest rows, a new session can receive an ordinal below an outstanding cursor and appear later in that scan. **Smallest fix:** allocate ordinals from a persistent monotonic counter, or explicitly defer and qualify the pagination guarantee until retention supplies one.

## Minor finding

7. **The storage warning omits the daemon log.** **Verified:** `data_bytes` counts SQLite, blobs and evidence, but excludes `via.log` and `via.log.1`, although the log lives in the state directory and can grow between starts (`docs/workstreams/rust-foundation/t4/design.md:537`, `docs/workstreams/rust-foundation/t4/design.md:889`). **Inference:** `over_warn_size` can remain false while VIA’s own log consumes space past the warning threshold. **Smallest fix:** include both log files in `data_bytes`, or name the field and warning as retention-managed data only.

## Could not verify

The envelope-member maxima, especially derived `bound.effective`, the RSS estimate, and actual WAL growth remain the design’s stated inferences or measurement gates.
