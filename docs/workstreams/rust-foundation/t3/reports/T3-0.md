## 2. Open questions that block the design

Each has a recommended answer, which the design already follows.

1. **Q1: Does `daemon stop --drain` close sessions durably?** C1 §7.1 lists
   "drain completed" as a cause of `closed`, and §3.14 says drain "gates every
   session `closing`". C1 defines no `session.closed` reason for drain.
   Closing every historical session on a routine drain would make them
   unresumable after the restart.
   - **Recommendation:** no. Drain's gate is the daemon-lifetime
     `daemon_stopping` refusal. Amend C1 §7.1 (A5).
   - **Alternative:** close every open session at drain end with a new
     reason `daemon_stop_drain`, reusing §6.3's idle-session pass.
2. **Q2: A daemon exit status for lock contention (A3).** F1 and F6 need the
   CLI to tell "another daemon owns the runtime root" from real startup
   failures (F3, F11).
   - **Recommendation:** exit 75 for `daemon.lock` contention only.
   - **Alternative:** the CLI polls the full 15 s budget after any child
     exit. That is correct but delays every F3 and F11 report by 15 s.
3. **Q3: SIGINT handler in the CLI (A6).** Coding-style §6 allows signal
   handlers only in daemon main and the anchor. Without a handler the CLI
   dies by signal: shells show 130, but `ExitStatus::code()` is `None`, so
   the F29 assertion "exit 130" cannot hold.
   - **Recommendation:** allow foreground `spawn` and `wait` a SIGINT handler
     that only exits 130.
4. **Q4: How the version mismatch restarts an idle daemon (A4).**
   `daemon/stop` needs `hello` first.
   - **Recommendation:** a mismatched `hello` on an otherwise idle daemon
     triggers the idle stop itself (`data.restart: "stopping"`).
   - **Alternative:** allow a plain `daemon/stop` before `hello`, which
     weakens the handshake rule.
5. **Q5: `event_end {reason: store_error}` is on the carried list.**
   - **Recommendation:** move it to Task 4, which builds follow. Task 3
     cannot deliver an end notice with no follow stream.
6. **Q6: The reserved Store lifecycle slot** (runtime §7, §8).
   - **Recommendation:** Task 4, with the Store request-side bounds already
     assigned to `via-jm4.7.8` (dispatch-design §11 "Scope"). Task 3's batch
     treats a full channel as skipped.
7. **Q7: The no-`wait` running-cancel reply (A8)** and the reading of C1
   §7.6 row precedence for deadline stops (A7).
   - **Recommendation:** as in design §3.3 and §2. These are clarifications,
     but Sol should confirm them, because tests will assert them.

The following are not blocking but need owner confirmation:

- idle exit ignores settled-uncertain and earlier-daemon holdings (§6.4);
- the 10 s continuous-read-failure latch (A10);
- the failure batch cancels only the affected session's queue (A11).

## 3. Current code that contradicts a contract

1. **C1, S1 scope.** Fake capabilities declare `cancel` and `close`
   unsupported, "not implemented in S1" (`crates/via-core/src/api.rs:863-864`),
   and no method exists. S1 scope and C1 include both verbs.
2. **C1 §3.14, runtime §7.** `daemon/status` hardcodes `health: "healthy"`,
   `idle: 0` and `closing: 0`, and reports `active` as a turn count, not a
   session count (`crates/via-cli/src/server.rs:516-521`). T3 fixes health and
   closing; the session counts stay with Task 4.
3. **Runtime §8.** The daemon has no 60 s idle exit (`server.rs:128-166`).
4. **C1 §7.6, S1 F21.** An unterminated final frame after exit is `protocol`,
   not `process_exited` (`crates/via-routes/src/runtime.rs:410-412`).
5. **C1 §1.** No exit 130, and the auto-started daemon shares the CLI's process
   group, so Ctrl-C kills it (`crates/via-cli/src/client.rs:124-145`). The
   idle daemon is not restarted on a version mismatch (`client.rs:253-255`).
6. **C1 §3.14.** Force does not close sessions that were idle at acceptance
   (`crates/via-core/src/engine/stop.rs:115-116`).
7. **Runtime §6.2, §7.** The final deadline runs from final-shutdown start, not
   from the first Store failure (`server.rs:260-261`). There is no 5 s
   diagnostic window. There is no 2 s bound on post-failure commit outcomes.
8. **Runtime §6.** Recovery never marks an unsealed connection incomplete
   (`crates/via-core/src/engine/recovery.rs:263-264`).
9. **Runtime §5, text inconsistency.** §5's allow-list names "vendor VIA
   marker". Host refuses `VIA_PROCESS_MARKER` in the vendor environment
   (`crates/via-host/src/host.rs:381-388`), and §5.1 says the private marker is
   never inherited. The code matches §5.1 and C1 §7.5 (no vendor marker
   discovery).
   - **Recommendation:** delete "vendor VIA marker" from §5.
10. **Runtime §6.1.** Managed directories, including `state/raw`, are created
    before `daemon.lock` and `store.lock` (`server.rs:93-98`). A startup that
    fails after bind leaves `via.sock` behind (`server.rs:109` vs the error
    returns at `:112` and in `open_engine`).
11. **C1 §8.1, truthfulness of `commit_outcome`.** A Store request refused
    because the channel is full was never sent, yet `Unavailable` counts as
    "may have committed" (`crates/via-core/src/engine/journal.rs:191-193`,
    `crates/via-store/src/runtime.rs:988-992`). A receipt then reports
    `commit_outcome: unknown` where `not_committed` is provable.
    - **Recommendation:** Task 4, with Store request-side refusal.
12. **Runtime §11.** The named failpoints `store.commit.fail_persistent` and
    `raw.sync.fail_persistent` do not exist, and `fail_io` fires for one
    occurrence only (`crates/via-store/src/failpoint.rs:203-230`). T3 adds the
    Store one (design §10); the raw one stays with Task 4.

Not contradictions, for the record:

- Plain `daemon stop` is refused while turns are active, which matches C1
  §7.1's `active` session state.
- The anchor's 200 ms TERM grace is within runtime §5.2's "at most 2 s".
- The wall-deadline `cancel.requested_at` is the projected deadline time
  (`drive.rs:431`). That is when the deadline occurred.

## 4. Slice plan (summary; normative detail in design §13)

`{S0 ∥ S1} → S2 → {S3 ∥ S4}`.

| Slice | Model | Scope |
|---|---|---|
| S0 | Opus 5.5 medium | split `engine.rs` and `server.rs` by responsibility; moves only |
| S1 | Opus 5.5 high | every Store, Host, Wire, Route and Adapter change (schema v5, Store ops, stop watch and interrupt, F21 exit mapping, pre-ARM gate, re-probe primitive, failpoints) |
| S2 | Opus 5.5 high | Core turn control: claims, cancel, close/closing, restart close completion, idle deadline; CLI `cancel` and `close`; F19–F21 scenarios |
| S3 | Opus 5.5 high | daemon lifecycle and failure: F1–F4, F6, F7, F11, F12 remainder, outstanding read, persistent read failure, F29, barriers, re-probe loop and status |
| S4 | Opus 5.5 medium | recovery evidence: F9, F22, F23, raw incompleteness, restart with a nondefault frozen value |

S1 is the largest slice. If its review shows that, it splits cleanly into
Store (S1a) and Host, Wire, Route and Adapter (S1b).
