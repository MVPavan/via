## Re-pointed latch tests

Each of these injected a not-committed failure and expected the latch.
Each now injects an escalation, or detects the latch differently.

- Unit `a_failed_cancellation_under_force_is_unclean_and_leaves_the_session_open`
  (`engine/tests.rs`, `5c4eef9`): both attempts of the forced cancellation
  fail, so it escalates.
- `s1_daemon_stop_store_failure_is_not_a_clean_exit` (`5c4eef9`, `0a2daf6`):
  - it expects the batch;
  - it detects the latch through `daemon/status` (`wait_latched`), because
    the socket stays up through the window.
- `s1_daemon_stop_force_after_store_failure_ends_failed_store` (`0a2daf6`):
  it detects the latch through `wait_latched`.
- `s1_close_outcome_retained_for_late_subscriber` (`s1_turn_control.rs`,
  `5c4eef9`): it escalates with a persistent terminal failure.

`s1_crash_points.rs` needed no re-point. Its only change is the helper
move in `f14a34a`.

## Choices where the design was ambiguous

Each choice keeps O1's split: scoped when the outcome is known, latched
when it is uncertain.

1. **Dispatcher cancellations in the restart handoff** also get row 9's
   one retry.
2. **Row 15's forced terminal** never latches when it did not commit.
3. **A corrupt outcome on a write** gives the reply `RECEIPT_UNKNOWN`.
4. **The batch's `turn.ended`** is the kept forced terminal, rewritten to
   `failed(store)` with the message `TERMINAL_LOST`.
5. **An absence-proof failure** is recorded once per re-probe pass, with
   scope `session`.
6. **`Store` cause, not launched, no cleanup** → `quiescent`
   (`terminal.rs`; row 3).
7. **`commit_submit_failed`** is armed through `store.commit.terminal`, the
   seam its transaction hits.
8. **The read streak's queueing** always comes from history
   (`turn.queued`), never from the unreadable row.
9. **At the streak deadline**, a failed history read rolls the claim back
   and escalates (a `Resolution` hook).
10. **The streak** resets on any `Step::Next`. `Step::Wait` leaves it
    unchanged. Only a failed read at or past the deadline fails the head.
    Retry wakes are `min(backoff, deadline − now)`.
11. **Read corruption latches** for:
    - dispatcher reads;
    - `read.rs` request reads (`turns`, `events`, `logs`);
    - `Engine::read_result`.

    The authentication and `session_snapshot` reads of `cancel` and
    `close`, the shutdown reads and the recovery reads keep their existing
    handling.
12. **Transient request read failures** are not recorded in
    `store_failure`.
13. **A cancel that meets `CorruptEvidence`** falls back to history for
    both owners. Transient failures stay a plain `store_error` for a
    request and retry for the dispatcher.
14. **The window** exists only if `failed_at` is set when serving returns
    after final-shutdown entry. Otherwise `closing` is sent first, as
    before.
15. **The S4 carried "unknown with pending cleanup"** case cannot be
    produced end to end: a durable `unknown` whose cleanup is still
    pending after a restart. The live-unknown test drives the same
    dispatcher path (`cancel_queued` behind `unknown`).
16. **After the latch, `force_queue` writes nothing.** A session with no
    affected turn keeps its queued turns `queued` for the restart handoff.
    `s1_f12_latch_cancel_and_close_return_store_error` asserts this
    (`cancelled,queued`).
17. **Test slack** against daemon bounds is 500 ms (`SLACK`).
18. **The unacknowledged order** (§3.3 "Drop without an acknowledgement")
    has only one reachable form: the cancel finds the turn `settling` and
    sends no order. The run loop acknowledges every order it settles with
    (`observe_order` at `settle`). Cancel's step 3 refuses a cancel that
    arrives after a force is accepted. So the test admits the cancel
    before the force, holding it at the new seam `core.cancel.admitted`.
19. **The unacknowledged variant** keeps its own test name, as does the
    never-committing variant and the failure half:
    - `s1_cancel_wait_across_force_handoff_unacknowledged`;
    - `s1_cancel_wait_across_force_handoff_terminal_not_committed`;
    - `s1_close_failed_closed_keeps_closing_count_after_failure`;
    - `s1_close_waiter_resolves_on_latch`.
20. **`s1_f12_latch_pipeline_orders_handoffs`**: both run loops (A's and
    B's) are forced. Which one reaches `core.run.before_handoff` first is
    not deterministic, and the controller holds one armed occurrence per
    point.
    - The test first holds B at its own handoff commit
      (`core.commit.before_send`). A commits nothing after its failure.
    - A takes occurrence 1 and is held.
    - Occurrence 2 is armed while A is held, then A is released and B is
      released into occurrence 2.
    - The first version armed occurrences 1 and 2 together. It failed with
      no acknowledgement of occurrence 1, because the second arm replaces
      the first.

  `store.commit.submission` also failing" → `store.commit.terminal` (choice
  7).

  pause after cancel's step 3, before the slot step; test builds only".

  `s1_close_waiter_resolves_on_force` and `s1_close_waiter_resolves_on_latch`.

  A session without an affected turn keeps its queued turns `queued` for
  the restart handoff (choice 16).

  found by the restart handoff are not recorded in `store_failure`

### Choices

1. **Decision 1.** The later uncertain failure is recorded with site
   `Raw`, outcome `Uncertain`, scope `turn`, as the first-failure branch
   already labels every latching Route kind. `NotCommitted` and `Raw`
   after a first failure stay unreported, as before: nothing new is
   uncertain.
2. **Decision 2, classification of a read.** A failed head read wrote
   nothing, so only corruption changes it (`of_read`: `Corrupt` stays,
   `Uncertain` and `WriterLost` on a read become `NotCommitted`). A receipt
   whose head read is corrupt reports `Receipt`/`Corrupt` under the
   caller's `admission` and replies the existing plain `store_error`.
3. **Decision 2, the test seam.** `store.sqlite.corrupt` fires on every
   read, so the head read's occurrence is not knowable from the harness. The
   new `store.sqlite.corrupt_head` fires on the session-head read
   (`NextSeq`) only. The end-to-end test restarts the daemon, because a
   head is read only when a slot has none: a restarted daemon keeps no
   slot for an idle session. The event and acceptance sites have no
   end-to-end form: their head is unknown only after an uncertain write,
   which already latched. The journal unit test covers `commit_event_at`;
   the acceptance site shares `of_read`.
4. **Decision 3, engine-level test.** I first wrote an end-to-end test
   (the run loop parked at `core.commit.before_send` while the vendor
   emits its last event and exits). It passed without the fix: Route
   completes only after its graceful close, a later Store write, so the
   last event reaches `observed_rx` before completion, and `tokio::select!`
   picks at random among ready branches. No deterministic end-to-end form
   exists, so it was removed. The engine test drives the extracted `drain`
   through a test-only `drain_queued`, with a record whose head read fails
   (a session Store does not hold), so the write is not committed.
5. **Decision 4.** The count is the sessions not yet visited when the pass
   sees the latch, plus those already counted. The unjoined sessions stay
   counted as before.
6. **Decision 5.** Only the handoff's failed corrupt row is recorded, as
   the live rule records only the corrupt row it fails. A corrupt row the
   handoff or a live cancel cancels (behind `unknown`, or for a close) is
   not recorded: its disposition is the cancellation, as before.
7. **Decision 6.** The uncertain (latching) pass error has no owner; it
   keeps the caller's scope (`Request` for the daemon-wide pass, the
   session for close's absence check) and records scope `daemon`.
8. **Decision 7, end to end with synthetic state.** S4's surviving-anchor
   harness does not give `pending`: restart verifies the anchor, stops it
   and proves absence, so the recovered turn is `forced`/`quiescent`. No
   product path writes `pending` into a durable envelope (the engine test
   `a_successor_waits_behind_a_cleanup_pending_predecessor` says so). The
   test therefore uses S4's crash-behind-running harness:
   - a restart held at the handoff's first queued-row read and killed
     leaves turn 1 durably `unknown` and turns 2–3 `queued`;
   - turn 1's cleanup is set to `pending` in Store while no daemon runs;
   - the next daemon's dispatcher waits: its predecessor reads, counted at
     `store.read.dispatch`, repeat while turns 2 and 3 stay queued;
   - the cleanup is set to `quiescent` while the daemon runs, and both
     turns end cancelled, never submitted, without a launch.
