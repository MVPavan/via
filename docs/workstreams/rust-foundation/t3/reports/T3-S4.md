## Blocked edit

**Where.** `crates/via-cli/tests/s1_crash_points.rs`, in
`s1_t2c_lost_handoff_cancellation_reply_fails_startup_then_admits`
(currently lines 2131–2134).

**What the test assumes.** It arms `store.commit.reply_lost` at occurrence
4. It assumes that recovery makes three commits for turn 1
(`cancel.requested`, `cancel.settled`, terminal), so that the handoff's
cancellation of turn 2 is the fourth commit.

**What changed.** Turn 1 had an armed anchor, so recovery now also commits
turn 1's `raw_log.incomplete` (§9). The handoff cancellation becomes the
fifth commit. The lost reply now hits turn 1's terminal instead, and the
test fails with `crash recovery failed: store_error: store_error`, not with
`restart handoff failed`.

**The exact edit:**

```diff
-            // Recovery commits turn 1's `cancel.requested`, `cancel.settled`
-            // and terminal; the handoff's cancellation of turn 2 is fourth.
+            // Recovery commits turn 1's `raw_log.incomplete`,
+            // `cancel.requested`, `cancel.settled` and terminal; the
+            // handoff's cancellation of turn 2 is fifth.
             let lost = "store.commit.reply_lost";
-            paths.failpoints.arm(lost, 4, "fail_io").map_err(infra)?;
+            paths.failpoints.arm(lost, 5, "fail_io").map_err(infra)?;
```

**Why the edit is in the test.** The alternative is to fold
`raw_log.incomplete` into the terminal transaction, as §7.2 row 6 does for
a live raw failure. That would make recovery's commit count unchanged, but:

- the recovery terminal path does not carry an extra event, and adding one
  would change the Store call;
- the `restart_cleanup` history check in the crash-points tests
  (`ends_with [cancel.requested, cancel.settled, turn.ended]`) would break
  in many tests instead of one.

The edit keeps the test's intent: the fault still hits the handoff's
cancellation.

## Design ambiguities: the choices made

1. **Unreadable anchor phase.** An owner with no readable phase (`phase:
   None`) counts as armed. Only an explicit `Intent` or `Identified` phase
   rules out a connection. Rationale: incompleteness is never under-claimed.
2. **Incomplete inventory.** If Host's anchor inventory is incomplete (a
   deadline or a failed page), every recovered turn is marked raw-incomplete.
   This is the same conservative reading.
3. **Where the event goes.** `raw_log.incomplete` is committed as its own
   event, before recovery's `cancel.requested`. It is not part of the
   terminal transaction (§7.2 row 6 is the live raw-failure path). If a
   `raw_log.incomplete` is already durable for the turn, from an earlier,
   interrupted recovery, it is not repeated.
4. **The connection id.** The id is derived as the dispatcher derives it:
   `c_<session suffix>` for turn 1 and `c_<suffix>t<n>` for later turns.
   `drive.rs`'s `connection_id` is private, and `drive.rs` is not S4's file,
   so `recovery.rs` has a documented copy, `recovered_connection`. A unit
   test pins the format.
5. **Corrupt rows are failed only at the head.** The handoff fails a corrupt
   row only when no predecessor is unresolved. A corrupt turn behind a
   queued or running predecessor is enqueued as usual, and the dispatcher's
   live rule (S5) meets it at the head. Otherwise the handoff would commit
   `turn.submitted` for a later turn while an earlier one is still queued.
   That would break per-session submission order. §7.3 says the handoff
   "parses the frozen values of every turn it would enqueue". This choice
   narrows that to the head.
6. **Corrupt rows on the cancel and close paths.** Take a row that the
   handoff would cancel (behind an `unknown` predecessor, or in a closing
   session). If Store itself cannot read it (`CorruptEvidence`), it is
   failed `failed(store)`, not cancelled, because `cancel_queued` cannot
   read it either. If only Core's `effective` parse would fail, it is not
   parsed on these paths (the rule concerns turns the handoff would
   enqueue), so it is cancelled as before.
7. **Failure message.** The corrupt-row failure is `failed`, class `Store`,
   `stop_reason` `error`, with message "a frozen value of the queued turn
   could not be read". `Handoff` gains a `failed` count.

### 1. The `unknown` barrier across a corrupt row

**The bug.** Take a row that Store cannot read, behind an `unknown`
predecessor. Round 0's handoff failed it through `commit_submit_failed`,
which gave it `submitted_at`. So the row became the latest submitted turn
for the next row. That next row then saw a `failed` predecessor instead of
the `unknown` one, and was enqueued to run. C1 P6 cancels it.

**The mechanism chosen.** The handoff cancels such a row, as it cancels the
rest of the queue behind an `unknown` turn. It does the same on a closing
session's close path. The coordinator suggested the alternative: look past
a corrupt-row failure to its predecessor. I did not use it, for two reasons:

- A cancelled turn is never submitted. So the barrier holds for every later
  reader of `predecessors()`, including:
  - the next handoff after a restart;
  - the live dispatcher (`drive.rs` `decide`) for any later `resume`.

  Look-past in the handoff alone would leave the dispatcher, which S4 does
  not own, seeing the `failed` row as the latest submitted turn.
- Cancelling needs no Store change. `insert_terminal` never reads
  `effective`. A queued turn's cancellation needs only `queued_at` and the
  `turn.queued` sequence, and the turn's committed events provide both.

**The new code.** `cancel_unreadable_turn` builds the same cancellation as
`drive.rs`'s private `queued_cancellation`. With the close cause, the
`cancel` is `acknowledged`/`quiescent`, as in design §3.2. It commits
through `commit_turn_ended_with`, with no dispatcher registration. A
cancellation that is not certainly durable fails startup (row 13).

This also reads §7.3 more closely than round 0 did. §7.3 applies the parse
rule to turns the handoff "would enqueue", and a turn behind `unknown` is
not one of them. Round 0's choice 6 (a Store-unreadable row on the cancel
or close path is failed) is replaced by this.

**Rows behind a pending `unknown`.** If the `unknown` predecessor's cleanup
is `pending`, a corrupt row behind it is no longer failed. It is enqueued
instead, and the dispatcher waits, then applies P6. Failing it would reopen
the same hole once the cleanup settles. No test covers this case: I know of
no way to produce a durable `unknown` with `pending` cleanup end to end.

### 2. A durable `raw_log.incomplete` carries its warning

`reconciled.raw_incomplete(..) || raw_logged`. A durable event gives the
envelope its warning whatever the current inventory shows. The choice that
an incomplete inventory counts as armed is unchanged; the coordinator

**The regression** follows the two-restart sequence:

1. Setup:
